# 第 05 章 · Token、上下文窗口与上下文工程

> 目标：搞懂三个天天挂在嘴边的词——**Token**（模型眼里的"字"）、**上下文窗口**（模型一次能"记住"多少）、**上下文工程**（怎么在有限的窗口里塞进最有用的信息）。读完这章，你会明白 DeepTutor 为什么在每次调用模型前要"检查上下文长度"，以及"为什么我的聊天记录太长会被压缩/截断"。

黑话先定义：**Token** 是模型处理文本的最小单位（不是"字"也不是"词"，而是按规则切出来的小碎片）；**上下文窗口（context window）** 是模型一次输入能容纳的全部 token 数量上限；**上下文工程（context engineering）** 是"在窗口有限的前提下，决定把哪些内容放进去、按什么顺序放"的设计学问。

---

## 5.1 Token：模型眼中的"字"不是你以为的"字"

### 5.1.1 为什么不能按"字"切？

我们人类数"我爱你"是 3 个字。但模型不是一个字一个字地"认"的——它要把文字变成数字向量（第 2 章的嵌入），而向量化需要一个稳定的"切分单位"。如果按"字"切，英文里 `run` 和 `running` 会被切成毫无关联的两个东西，浪费学习量。

所以模型用一套**分词器（tokenizer）**把文本切成 token。规则大概是：

- 英文：常见单词是 1 个 token，长单词或生词会被切成 2–3 片。
- 中文：通常 1 个汉字约 0.6–1.5 个 token（各家模型不同），成语、常见词可能合并成一个 token。
- 标点、空格也算 token。

```text
英文示例（示意，非精确）:
  "Hello, world!"  →  [Hello] [,] [ world] [!]      ≈ 4 tokens
中文示例（示意，非精确）:
  "你好，世界！"    →  [你好] [，] [世界] [！]         ≈ 4 tokens
```

### 5.1.2 为什么要关心 token？

因为**钱**和**窗口**都按 token 算：

1. **计费**：大模型 API 按"输入 token 数 + 输出 token 数"收费。
2. **窗口上限**：一次请求所有输入（系统提示词 + 历史消息 + 工具定义 + 检索结果）加起来不能超过窗口。
3. **性能**：上下文越长，模型"回想"关键信息越吃力（业内叫"大海捞针"难题），推理也越慢。

> **提示 · 直觉记忆**
>
> Token 就是模型世界的"计价单位"和"内存单位"。你给模型喂的每一句话，先被切成一串 token，才进得了模型。

## 5.2 上下文窗口：模型的"一次性记忆"

### 5.2.1 窗口不是硬盘，是"桌面"

把上下文窗口想成一张**桌面**：一次只能摊开这么多材料。放不下怎么办？要么把旧材料收起来（丢弃/压缩），要么让新来的等一等。

```text

  组装 messages（系统提示+历史+工具结果）
        │
        ▼
  guard_context_window(messages)   ← 第 05 章的主角：超限就处理
        │
        ▼

        │
        ▼

```

> **说明 · 为什么守卫在"循环"里而不是"调用"里**
>
> 调用模型的地方很多（聊天、检索总结、记忆合并……），如果每个地方都自己判断窗口，代码会重复且容易漏。DeepTutor 把守卫做成**能力（Capability）的钩子**，统一在循环这一步把关——一处实现，处处生效。这就是"横切关注点"的设计思路。

## 5.3 上下文工程：有限窗口里的"信息排兵布阵"

### 5.3.1 三个问题

窗口有限，但想塞的东西无限。上下文工程要回答三个问题：

1. **放什么**：系统提示词、历史消息、工具定义、检索到的知识库片段、用户当前问题——优先级怎么排？
2. **放多少**：历史消息留最近 20 条还是 50 条？检索片段留 5 个还是 20 个？
3. **丢了怎么办**：放不下的旧消息，是直接扔掉，还是压缩成摘要（第 26 章的三层记忆里的 L2 就是这个角色）？

### 5.3.2 通用排布规律

经验上，一段好的上下文大致是这个顺序（各家略有差异）：

```text
┌────────────────────────────────────────────┐
│ 1. 系统提示词（角色、规则、能力清单）        │  ← 最不该被截掉
├────────────────────────────────────────────┤
│ 2. 工具定义（function schema，第 07 章）     │  ← 模型要"知道能干什么"
├────────────────────────────────────────────┤
│ 3. 记忆/画像（第 26 章 L3 个性化摘要）       │
├────────────────────────────────────────────┤
│ 4. 检索到的知识库片段（第 27 章 RAG）        │
├────────────────────────────────────────────┤
│ 5. 历史对话（越近的越重要）                  │  ← 最先被压缩的
├────────────────────────────────────────────┤
│ 6. 当前用户问题                            │  ← 必须完整保留
└────────────────────────────────────────────┘
```

**核心原则：越"决定了这轮回答方向"的内容越靠前、越不可截断；越"只是背景"的内容越靠后、越先被丢弃或压缩。**

### 5.3.3 上下文工程的三种武器

| 武器 | 作用 | DeepTutor 里的体现 |
|------|------|-------------------|
| **裁剪（truncate）** | 丢掉最旧/最不重要的历史 | 历史消息按条数/按 token 预算裁剪 |
| **压缩（summarize）** | 把一段历史变成一句话摘要 | `services/memory/consolidator/`（L2 记忆合并，26 章） |
| **注入（inject）** | 把外部知识精确塞进窗口 | RAG 检索片段拼接（27 章） |

### 5.3.4 一个具体例子：系统提示词为什么"贵"

系统提示词每一轮请求都要跟着发一遍，它越长，每轮都多花 token 钱。所以工程上系统提示词要**精炼**：只放角色、规则、能力清单，把大段教材内容放进知识库（需要时检索），而不是全塞进系统提示词。这就是第 12 章"提示缓存"能省钱的前提之一——不变的头部内容被缓存，只有变化的尾部重新计费。

> **注意 · 新手最容易踩的坑**
>
> "既然窗口有 128k，我就把整本教材塞进提示词"——这是典型的错误。窗口大不等于效果好：超长上下文既贵又容易让模型"忘"关键信息。正确的做法是**按需检索**（RAG）而不是全量塞入。

## 5.4 DeepTutor 里的"窗口相关设置"在哪

DeepTutor 的运行时设置都是 JSON 文件（`data/user/settings/*.json`），窗口相关的配置集中在 LLM provider 设置里。命令行或 Web 设置界面里一般能看到类似：

```json
{
  "model": "gpt-4o",
  "max_tokens": 4096,
  "context_window": 128000
}
```

- `model`：用哪个模型（决定 `default_context_window_for_model` 查哪张表）。
- `max_tokens`：**单次输出**上限。
- `context_window`：**输入窗口**上限；不写就让系统按模型自动推断（`resolve_effective_context_window`）。

> **提示 · 一句话记住本章**
>
> Token 是模型的"字"，窗口是模型的"桌面"。上下文工程就是**在有限的桌面上，把最该放的放上去，放不下的先压缩再丢弃**。DeepTutor 在 `loop.py:220` 调用模型前统一做守卫，在 `context_window.py` 统一算窗口。
