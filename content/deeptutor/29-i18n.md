# 第 29 章 · i18n 与多语言

"i18n" 是 *internationalization*（国际化）的缩写——i 和 n 之间夹了 18 个字母，程序员图省事就这么叫了。它的目标很朴素：**让同一套程序，对不同语言的用户显示不同语言的界面和文案**，而不是把英文写死在代码里。

DeepTutor 把多语言当成一等公民（first-class feature）。本章我们看它怎么做到"界面文案、状态提示、能力提示词"三处都双语化，以及你如果想加一种新语言该动哪里。代码在 `deeptutor/i18n/`。

## 先懂直觉：为什么"写死英文"行不通

假设你把按钮文字 `"Submit"` 直接写在代码里。现在想支持中文，就得满世界找这个字符串、改成判断。几百个地方改下来，必然漏、必然乱。

正确做法是：**把所有可显示的文案集中管理，按语言查表**。代码里只写"我要显示某个 key 对应的当前语言文案"，至于这个 key 在中文下是什么、英文下是什么，去一张"翻译表"里查。DeepTutor 正是这么做的。

> **黑话解释**："key（键）"在这里指文案的编号，比如 `chat` 能力的描述。代码始终用 key 来引用文案，真正显示时再翻译成当前语言。这样加语言只需往表里加一行，不用动逻辑。

## 第一处双语：界面元数据（metadata_i18n）

最直观的双语，是设置界面里那些"能力"和"工具"的中文/英文说明。比如"chat"能力，英文是 *"Default agentic chat with tools…"*，中文是 *"默认智能聊天，支持工具…"*。

这些文案集中放在 `deeptutor/i18n/metadata_i18n.py`。它用两张大表：

- `_CAPABILITY_DESCRIPTIONS`：每个能力的双语描述，见 `deeptutor/i18n/metadata_i18n.py:5`；
- `_TOOL_DESCRIPTIONS`：每个内置工具的双语描述，见 `deeptutor/i18n/metadata_i18n.py:36`。

每张表的结构是 `{"key": {"en": "...", "zh": "..."}}`。从 `deeptutor/i18n/metadata_i18n.py:5` 可以看到一个真实例子：`chat` 能力同时存了英文和中文两行。

提供两个查询函数：

- `capability_description_i18n(name, fallback)`：按能力名取双语字典，找不到就返回兜底，见 `deeptutor/i18n/metadata_i18n.py:76`；
- `tool_description_i18n(name, fallback)`：按工具名取，见 `deeptutor/i18n/metadata_i18n.py:83`。

真正"按当前语言挑一句话"的是 `localized_description`，见 `deeptutor/i18n/metadata_i18n.py:90`。它的判断很直接：看传入的 `language` 是不是以 `zh` 开头，是就用中文，否则英文：

```python
lang = "zh" if (language or "en").lower().startswith("zh") else "en"
return values.get(lang) or values.get("en") or values.get("zh") or ""
```

> **提示 · 为什么要保留英文兜底？**
>
> 注意最后一行 `or values.get("en") or values.get("zh")`——就算某语言的文案缺失，它也尽量返回点东西，而不是空字符串或报错。这是 i18n 的黄金法则：**永远有退路（fallback）**。一个新语言刚加、翻译不全时，用户至少能看到英文，而不是空白。

## 第二处双语：能力运行时的状态文案（status_i18n）

能力（capability）在运行时会往聊天界面**实时推送状态消息**，比如"正在检索知识库…""正在生成题目…"。这些消息也得跟着用户语言走。

这部分在 `deeptutor/i18n/status_i18n.py`。核心是 `StatusI18n` 类，见 `deeptutor/i18n/status_i18n.py:23`。它怎么工作：

1. 构造时传入 `name`（状态文件名叫什么）、`language`（用户语言）、`module`（属于哪个能力的提示词模块），见 `deeptutor/i18n/status_i18n.py:34` 的 `__init__`；
2. 它惰性加载对应的提示词文件，从中取出 `status` 这张映射表（key → 文案），见 `deeptutor/i18n/status_i18n.py:41` 调用 `get_prompt_manager().load_prompts`；
3. 代码里任何原本写死英文的地方，改成调 `t(key, default, **kwargs)` 来取本地化文案，见 `deeptutor/i18n/status_i18n.py:49` 的 `t` 方法。

`t` 方法支持 `{name}` 这类占位符，用 `str.format` 填充（见 `deeptutor/i18n/status_i18n.py:54`）；如果某个 key 缺失或文件缺失，就退回 `default` 参数——又一处兜底。

> **约定**：状态文案放在能力自己的提示词模块下，文件名形如 `prompts/{en,zh}/<name>.yaml`，里面只有一个顶层的 `status:` 映射。这样"状态文案"和"LLM 提示词"紧挨着，翻译时不用来回翻文件。这套约定写在 `deeptutor/i18n/status_i18n.py:8` 的模块说明里。

## 第三处双语：能力提示词本身（prompts/{en,zh}）

前两处是"给界面看的文案"，但真正喂给大模型、决定它"怎么想、怎么答"的**提示词（prompt）**也得双语。否则中文用户得到的还是英文思考框架。

DeepTutor 把每个能力的提示词按语言分目录存放。目录结构是：

```text
deeptutor/agents/chat/prompts/
    en/        ← 英文提示词
    zh/        ← 中文提示词
deeptutor/agents/question/prompts/
    en/
    zh/
deeptutor/capabilities/solve/prompts/
    en/
    zh/
deeptutor/agents/research/prompts/
    en/
    zh/
...
```

也就是说，几乎所有能力（chat、question、solve、research、visualize、mastery、co_writer……）都有自己的 `prompts/en` 和 `prompts/zh` 两套。`status_i18n` 正是从这套目录里加载 `status` 表的——它和提示词共用同一套"按语言取文件"的机制。

> **说明 · 三处双语各自服务谁？**
>
> - *界面元数据*（metadata_i18n）：给"设置页、能力列表"看的，用户读得见。
> - *状态文案*（status_i18n）：给"能力运行时的进度条、状态行"看的，用户读得见。
> - *能力提示词*（prompts/{en,zh}）：给"大模型自己"看的，用户通常看不见，但决定了回答质量。
> 
> 三者合在一起，才叫"从里到外都双语"。

## 对外出口：i18n 包的统一门面

`deeptutor/i18n/__init__.py` 把上面两类 helper 汇总导出，见 `deeptutor/i18n/__init__.py:12`：

- `capability_description_i18n`、`tool_description_i18n`、`localized_description` 来自 metadata_i18n；
- `StatusI18n` 来自 status_i18n。

外部模块统一从 `deeptutor.i18n` 引入，不必关心底层分到几个文件。

## 语言从哪来、到哪去

整条链路是这样的：

```text
用户在前端选语言（"en" / "zh"）
        │
        ▼
请求带上 language 字段，传进后端
        │
        ├─▶ metadata_i18n.localized_description(..., language)
        │        → 能力/工具的中文或英文说明
        │
        ├─▶ status_i18n.StatusI18n(name, language, module=...)
        │        → 运行时状态的中文或英文文案
        │
        └─▶ PromptManager.load_prompts(language=...)
                 → 对应语言的 LLM 提示词（en/ 或 zh/ 目录）
```

注意：`language` 在三个地方都被一以贯之地往下传，所以"用户选了中文"能一路贯穿到模型提示词。这就是 i18n 把"语言"当成一个**贯穿全局的参数**来对待的典型做法。

## 如何新增一种语言

假设你现在要加日语（`ja`）。按上面的结构，改动是收敛的：

1. **界面元数据**：在 `metadata_i18n.py` 的两张表里，给每个 key 增加 `"ja"` 字段。若要支持"整张表按语言查"，可顺手改 `_CAPABILITY_DESCRIPTIONS` 的结构（目前是 en/zh 双键）。
2. **状态文案**：在每个能力的 `prompts/ja/<name>.yaml` 里补 `status:` 映射，并把 `StatusI18n` 的兜底语言判断扩展（目前 `localized_description` 只认 zh，需让其认得 ja，见 `deeptutor/i18n/metadata_i18n.py:91`）。
3. **能力提示词**：为每个能力的 `prompts/ja/` 目录写一份日文提示词。

下面用一个最小示例，演示"加一个能力描述"要改哪里：

```python
# deeptutor/i18n/metadata_i18n.py 内 _CAPABILITY_DESCRIPTIONS
"my_new_cap": {
    "en": "Does something useful in English.",
    "zh": "用中文做一件有用的事。",
    # 加日语时补一行：
    # "ja": "日本語で役立つことをする。",
},
```

> **提示 · 别急着"写死新语言名"**
>
> 新增语言时，最容易出错的是把 `"ja"` 散落在十几个 `if lang == "ja"` 判断里。更稳的做法是**只在"语言→文案"这一处集中判断**（就是 `localized_description` 和 `StatusI18n.t`），其余地方永远传 `language` 参数、靠查表返回。这样加第 N 种语言时，逻辑代码一行都不用改，只加翻译数据。

## 第四处兜底：core/i18n.py 的全局 t()

除了 `deeptutor/i18n/` 包里的两个 helper，代码里还有一层更通用的 i18n 工具 `deeptutor/core/i18n.py`：

- `_parse_language(language)`：把各种写法归一化成标准语言码（如 `zh-CN` → `zh`），见 `deeptutor/core/i18n.py:8`；
- `current_language(default="en")`：取"当前语境下的语言"，见 `deeptutor/core/i18n.py:113`；
- `t(key, default, language=None, **kwargs)`：按 key + 语言取翻译文案，支持占位符，见 `deeptutor/core/i18n.py:122`。

它和 `metadata_i18n` / `status_i18n` 是同一哲学的两套实现：前者面向"产品代码里零散的字符串"，后者面向"能力和工具的元数据/状态"。无论哪套，都遵守"key 查表 + 兜底"的原则。

## 状态文案 YAML 长什么样

前面说状态文案放在 `prompts/{en,zh}/<name>.yaml`，里面只有一个顶层 `status:` 映射。一个最小示例：

```yaml
# deeptutor/agents/chat/prompts/zh/<name>.yaml
status:
  thinking: "正在思考…"
  retrieving: "正在检索知识库：{kb_name}"
  done: "已整理完成"
```

`StatusI18n.t("retrieving", "Retrieving {kb_name}", kb_name="数学库")` 会取出中文的 `"正在检索知识库：数学库"`。注意 `{kb_name}` 是占位符，由 `str.format` 填充（见 `deeptutor/i18n/status_i18n.py:54`）。这就是"状态文案跟着语言、还能动态带参数"的实现方式。

## 为什么是"三层"而不是"一处搞定"

你可能会问：既然都是双语，为什么不把所有文案塞进一张大表？DeepTutor 分成三层是有道理的：

- **变更频率不同**：界面元数据很少改；状态文案跟着能力的运行逻辑走，常改；能力提示词最"重"，是模型行为的核心，改动最慎重。分开后，改状态文案不会影响提示词，反之亦然。
- **归属不同**：界面元数据归"产品/设置"，状态文案和提示词归"能力开发者"，放在各自 `prompts/{en,zh}` 目录下，谁维护谁负责。
- **加载成本不同**：状态文案只在一个能力运行时加载自己那份；提示词也是按需加载。集中成一张巨表反而加载慢、易冲突。

> **说明 · 一个常见坑：翻译了却"不生效"**
>
> 新人加了一种语言，发现界面还是显示英文。十有八九是漏了"兜底语言判断"那一步——`localized_description` 目前只认 `zh`（见 `deeptutor/i18n/metadata_i18n.py:91`），如果没把它扩展成也认你的新语言码，查表永远走不进新语言分支。记住：i18n 的"切换"逻辑必须集中在"语言→文案"这一处，别把语言判断散落到各处。

## 三处双语的"加载链路"再细化

前面分别看了三处双语，这里把它们怎么被"加载"说得更具体：

- **界面元数据**是"主动查表"：前端要显示能力列表时，调 `capability_description_i18n` / `tool_description_i18n`，当场按语言取，见 `deeptutor/i18n/metadata_i18n.py:76`、`:83`；
- **状态文案**是"被动注入"：每个能力的 `run()` 开头 `new` 一个 `StatusI18n`，之后凡是原本写死英文的地方改成 `t(key, ...)`，运行时按当前语言取，见 `deeptutor/i18n/status_i18n.py:34`、`:49`；
- **能力提示词**是"按目录加载"：提示词管理器根据 `language` 选 `en/` 还是 `zh/` 目录下的文件，见 `deeptutor/i18n/status_i18n.py:41` 调用的 `load_prompts`。

三者都接收一个 `language` 参数，而这个参数来自用户请求——所以"用户选中文"能一路穿透到最里层的提示词。

## 状态文案与界面元数据的边界

容易混淆：两者都是"给界面看的文案"，区别在哪？

- **界面元数据**是**静态**的——一个能力"是什么"的描述，不会随运行变。比如 chat 永远是"默认智能聊天…"。
- **状态文案**是**动态**的——能力运行时流式吐出的进度，会带参数、会随阶段变。比如"正在检索知识库：{kb_name}"，每次检索的库名不同。

所以前者用简单的"key→双语文案"大表（`metadata_i18n.py`），后者用"按能力分文件、支持占位符"的 YAML（`status_i18n.py`）。结构不同，是因为**更新频率和动态程度不同**。

## 一个具体例子：加日语要动几处

假设 DeepTutor 要支持日语 `ja`，从"零"到"能用"，改动是：

```text
1. metadata_i18n.py
   _CAPABILITY_DESCRIPTIONS / _TOOL_DESCRIPTIONS
   每个 key 增加 "ja" 字段

2. localized_description（deeptutor/i18n/metadata_i18n.py:90）
   把只认 "zh" 的判断，扩展成也认 "ja"
   （否则查表永远走不进 ja 分支）

3. 每个能力的 prompts/ja/<name>.yaml
   补 status: 映射（供 StatusI18n 用）

4. 每个能力的 prompts/ja/*.yaml
   补完整的日文 LLM 提示词

5. （可选）core/i18n.py 的 current_language / t
   若产品代码里也用了全局 t()，同步扩展
```

注意第 2 步最关键也最易漏——**只加翻译数据、不改"语言判断"，界面仍显示英文**。这就是 i18n 新手最常见的坑（呼应前面 `deeptutor/i18n/metadata_i18n.py:91` 的讨论）。

## 常见误区

- **误区一："i18n 就是把英文翻译成中文。"** 错。它是"让程序支持任意多种语言，且加语言只加数据不改逻辑"。中文只是目前已支持的一种。
- **误区二："在代码里写 if lang=='zh' 分支就行。"** 危险。语言判断应集中在"语言→文案"这一处（如 `localized_description`），散落的 `if lang` 会让加第 N 种语言时到处改、必漏。
- **误区三："提示词不用翻译，模型看得懂英文。"** 不对。提示词决定模型的"思考框架和语气"，中文用户配英文提示词，模型回答容易中英混杂、不符预期。所以 `prompts/{en,zh}` 双语化是必要的。

## 全局 t()：产品代码里的零散字符串

前面讲的 `metadata_i18n` / `status_i18n` 服务于"能力/工具"这一层。产品其它地方（比如某些通用提示、日志外的用户可见串）若也要双语，用的是更通用的 `deeptutor/core/i18n.py`：

- `_parse_language(language)`：把 `zh-CN` 这类写法归一化成 `zh`，见 `deeptutor/core/i18n.py:8`；
- `current_language(default="en")`：取"当前语境下的语言"，见 `deeptutor/core/i18n.py:113`；
- `t(key, default, language=None, **kwargs)`：按 key + 语言取文案、支持占位符，见 `deeptutor/core/i18n.py:122`。

它和前面两套是同一哲学的两类实现：能力层用"定向 helper"，产品层用"通用 t()"。无论哪套，都遵守"key 查表 + 兜底"。

## core/i18n.py 的翻译表 _MESSAGES 长什么样

前面说 `core/i18n.py` 是"通用 t()"，它的翻译数据存在模块顶层的 `_MESSAGES` 字典里，见 `deeptutor/core/i18n.py:15`。结构和前两处一样，也是"语言码 → {key: 文案}"两层：

- 顶层是两个语言：`"en"` 和 `"zh"`，见 `deeptutor/core/i18n.py:16` 与 `deeptutor/core/i18n.py:69`；
- 第二层是大量 key，比如 `"api.partner_not_found"`（英文 `"Partner not found"` / 中文 `"未找到伙伴"`），见 `deeptutor/core/i18n.py:20` 与 `deeptutor/core/i18n.py:73`；
- 文案里同样支持 `{name}` 占位符，比如 `"Persona 已存在：{name}"`，见 `deeptutor/core/i18n.py:27`。

`t()` 取文案时的兜底顺序很关键，见 `deeptutor/core/i18n.py:124`：

```python
text = _MESSAGES.get(lang, {}).get(key) or _MESSAGES["en"].get(key) or default
```

意思是：先用当前语言查；查不到就退回英文 `_MESSAGES["en"]`；再查不到才用调用方给的 `default`。这正呼应了前面反复强调的 i18n 黄金法则——**永远有退路**。

> **提示 · 为什么三处双语都是"双层字典"？**
>
> `metadata_i18n` 用 `{"chat": {"en":..., "zh":...}}`，`core/i18n` 的 `_MESSAGES` 用 `{"en": {key:...}, "zh": {key:...}}`——两者只是"外层是能力名还是语言码"的差别，本质都是"两层查表 + 兜底"。记住这个结构，你换到任何一层都能一眼看懂。

## 全局 t() 取文案的完整流程

把 `current_language` 和 `t` 串起来，一次取文案是这样的：

```text
t("api.partner_not_found", "Partner not found", language="zh", name="Bob")
        │
        ▼
_parse_language("zh") 或 current_language() → "zh"   (core/i18n.py:8 / :113)
        │
        ▼
_MESSAGES["zh"].get("api.partner_not_found") → "伙伴未找到"
        │  （该 key 缺失则退回 _MESSAGES["en"]，再缺失才用 default）
        ▼
text.format(name="Bob") → "伙伴未找到：Bob"          (core/i18n.py:124 / :127)
```

注意 `t()` 自己也会先算语言（见 `deeptutor/core/i18n.py:123`）：如果你传了 `language` 就用它，否则自动调 `current_language()` 取全局语言。所以产品代码里散落的字符串也能跟着用户语言走，无需每个调用都手动传语言。

## 加一种语言时，_MESSAGES 要补什么

回到"加日语"的例子：`metadata_i18n` 的 `_CAPABILITY_DESCRIPTIONS` 是"能力 → {en,zh}"结构，加 ja 要在每个能力下加 `"ja"` 字段（见 `deeptutor/i18n/metadata_i18n.py:5`）；而 `core/i18n.py` 的 `_MESSAGES` 是"语言 → {key}"结构，加 ja 要在顶层多一个 `"ja": {...}` 分支（见 `deeptutor/core/i18n.py:15`）。两者补数据的位置不同，但都是"只加翻译、不改查表逻辑"。这正是 i18n 可维护的根本原因。

## 双语化的工程收益

为什么 DeepTutor 把多语言做这么重？因为教育产品面对的是全球学习者，收益很直接：

1. **降低使用门槛**：中文用户全程中文界面 + 中文提示词，模型回答更贴合语言习惯。
2. **可维护**：加语言只加翻译数据，逻辑零改动（见前面"加日语"的例子）。
3. **可兜底**：任一语言缺失都退回英文，不会空白或崩溃。
4. **分层清晰**：界面、状态、提示词各管各的，改一处不影响另一处。

> **提示 · 给想深入源码的人的阅读顺序**
>
> `i18n/metadata_i18n.py`（界面元数据）→ `i18n/status_i18n.py`（状态文案 + prompts/{en,zh} 约定）→ `core/i18n.py`（通用 t()）→ 随便挑一个能力的 `prompts/zh/<name>.yaml` 看真实翻译长什么样。顺着"查表→兜底→分层"这条线，i18n 全貌就清楚了。
