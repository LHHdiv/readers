# 第 12 章 · 提示缓存（Prompt Cache）与成本经济

> 目标：搞懂"缓存"在智能体系统里到底有多少种、各解决什么问题。你会看到：**提示缓存（Prompt Cache）** 是模型服务商侧的省钱机制；而 DeepTutor 本地还养着一整套自己的缓存（解析缓存、嵌入缓存、检索缓存、限流），每一层都在回答"能不能少算一次"。读完这章，你能脱口说出"这个缓存缓的是什么、什么时候失效"。

黑话先定义：**缓存（cache）** 是把"算过一次的结果"存起来，下次遇到同样的输入直接取，不再重算；**命中（hit）/ 未命中（miss）** 是"取到了 / 没取到"；**失效（invalidation）** 是"决定这份缓存该作废了"的规则。**提示缓存（Prompt Cache）** 特指模型服务商对"相同的前缀提示词"跳过重新计算、只收更低价格的机制。

---

## 12.1 为什么智能体系统特别需要缓存

普通聊天，每次请求内容变化大，缓存收益有限。但**智能体**的请求有个显著特点：**前缀高度稳定**。

- 系统提示词（角色、规则、工具清单）每轮都一样；
- 长对话里，前面的历史消息反复出现；
- 工具定义（function schema）整个会话不变。

而大模型 API 是按 token 计费的，每次请求这些不变的 token 都重新计费。**只要能把"不变的"复用，"变的"单独算，就能大幅省钱+提速**。这就是提示缓存的经济学。

```text
一次带缓存的请求计价示意（概念）:

  输入 = [系统提示 2k tokens][历史 6k tokens][本次问题 100 tokens]
              │            │              │
         服务商缓存命中   缓存命中       未命中(新)
         (只收低价)     (只收低价)       (全价)
```

> **说明 · 一个关键直觉**
>
> 缓存是**分层**的：服务商管"模型计算层"的缓存（提示缓存），你的程序管"自己应用层"的缓存（解析/嵌入/检索）。两层目的不同：前者省钱，后者省时间。

## 12.2 提示缓存（Prompt Cache）：模型服务商的机制

### 12.2.1 它是什么

主流模型服务商（OpenAI、Anthropic、DeepSeek 等）都提供提示缓存：当你发送的**前缀**与之前某次请求相同，服务商可以跳过前缀的重新计算，只收"缓存读取"的低价（通常便宜 50%–90%），并加快响应。

- **不需要你改代码**，只要请求方式满足条件（如 OpenAI 的自动缓存、Anthropic 需在消息里标记 `cache_control`），服务商自动生效。
- 缓存有 TTL（一般几分钟到几小时）：太久没用，缓存过期，下次全价重算。

### 12.2.2 工程上怎么配合

要让提示缓存命中率高，开发时要做到：

1. **稳定前缀**：系统提示词、工具定义尽量不变，不要每轮动态插入随机内容。
2. **固定顺序**：历史消息按固定顺序组织，避免"把最新消息插到最前面"这类破坏前缀的操作。
3. **分块标记**（Anthropic 风格）：在"可能变"的内容边界打 `cache_control` 断点，让服务商知道缓存到哪为止。

DeepTutor 这类系统天然适合：它的系统提示词 + 工具 schema 每轮稳定，前缀命中率高，成本结构比"每次全价"友好得多。

## 12.3 DeepTutor 本地的四类缓存

提示缓存是"模型服务商那边的省钱"，而 DeepTutor 自己代码里还维护着一批缓存，属于"自己应用层的省时间"。逐个看：

### 12.3.1 解析缓存：文档解析结果按内容寻址

用户上传 PDF/DOCX 后要解析成结构化文本（第 27 章 RAG 的前提）。同一份文档被反复解析很浪费，所以 DeepTutor 有内容寻址的解析缓存 `deeptutor/services/parsing/cache.py`：

```text
缓存目录结构（cache.py:8 注释）:

  parse_cache/<source_hash[:2]>/<source_hash>/<signature>/
      ├── ... 解析产物文件 ...
      └── .ready        ← 全部写完才打这个标记（cache.py:74）
```

关键设计：

- **内容寻址**：key 是 `source_hash`（文件内容哈希），文件内容变一点，哈希就变，自动"失效"——不需要手动清缓存。
- **签名化**：key 还带 `sig_hash`（解析器版本/参数签名）。换了解析器版本，签名变，旧缓存自动不命中，避免"用旧算法解析的新文件"。
- **原子就绪**：最后才写 `.ready` 标记（`cache.py:74`），防止读到半成品。

> **提示 · 失效策略总结（解析缓存）**
>
> 不靠时间，靠**内容哈希 + 解析器签名**。文件变了、或解析逻辑变了，key 自然对不上 → 自动失效。这种"内容即版本"的思路，比"定时清缓存"可靠得多。

### 12.3.2 嵌入缓存：同一个文本别重复向量化

把文本转成向量（embedding）也要花钱、花时间。如果用户反复问同一类问题、或知识库反复检索同一批片段，同样的文本没必要每次都重新向量化。DeepTutor 的 RAG 层对嵌入结果做缓存：key 通常是"文本哈希 + 嵌入模型签名"，命中就直接拿向量。相关机制与"嵌入版本签名"（`deeptutor/services/rag/embedding_signature.py`）配合，第 28 章会详细展开。

### 12.3.3 检索缓存 / 索引版本化

检索结果也可以缓存（同样的查询、同样的索引，短期内结果一样）。而"索引版本化"（`deeptutor/services/rag/index_versioning.py`）管的是更狠的失效：**只要文档集合、切分参数或嵌入模型变了，整个索引版本号就变**，所有旧检索结果自动作废。详见第 28 章。

### 12.3.4 限流控制器：不是缓存，但也是"省"的一种

`deeptutor/services/llm/traffic_control.py:13` 的 `TrafficController` 管的是**请求频率**：


它"缓存"的不是结果，而是**节流**：避免一次涌出 100 个并发请求把服务商打爆或被限流封号。这和"缓存省时间"互补——缓存是"少算"，限流是"稳算"。

## 12.4 缓存的通用设计要点（可迁移到你自己项目）

1. **key 要"内容化"**：尽量用内容的哈希做 key，而不是文件名/时间戳。内容变了 key 自然失效。
2. **版本要进 key**：算法、模型、参数任何一变，key 都要跟着变（否则会用到过期结果）。
3. **原子写入**：先写数据、最后写就绪标记，防止读到半成品。
4. **缓存要可观测**：记录命中率，命中率过低说明 key 设计有问题。
5. **区分省钱和省时**：服务商的提示缓存省钱，本地缓存省时间，各自目标不同、都要有。

> **注意 · 新手最常犯的错**
>
> 用"时间 TTL"作为唯一失效手段，结果文档更新后半天内还读到旧解析结果。正确做法：**内容哈希驱动失效**（如 cache.py），TTL 只做兜底。
