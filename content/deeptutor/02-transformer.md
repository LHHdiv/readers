# 第 02 章 · Transformer 与注意力机制直觉

> 目标：不写一个公式，把 Transformer 里最核心的"自注意力"讲到你能自己画出来。读完这章，你会明白为什么模型能读懂"它"指代谁、为什么上下文越长越贵、为什么模型是从左往右一个词一个词吐出来的——而这最后一点，直接决定了 DeepTutor 的循环协议怎么设计。

## 2.1 先问一个人类问题

请你读这句话，然后告诉我"它"指的是什么：

```text
小明把书放进书包里，因为它太重了。
小明把书放进书包里，因为它太空了。
```

第一句的"它"是**书**，第二句的"它"是**书包**。你读的时候几乎没有停顿，但你的大脑其实做了一件很复杂的事：**读到"它"的时候，你回头扫了一遍前面所有的词，并判断哪个词跟"它"关系最大。**

而且判断依据不只是距离，还得结合"重"和"空"这两个形容词的含义。

**自注意力（Self-Attention）做的就是这件事。** 整章你只要记住这一句话，剩下的都是细节。

> **说明 · 为什么这章值得花时间**
>
> 你可能觉得"我又不造模型，懂这个干嘛"。三个理由：
> 1. 你会理解**为什么上下文长度是硬约束**，从而看懂第 5 章的上下文工程和 DeepTutor 的窗口守卫。
> 2. 你会理解**为什么模型只能从左往右生成**，从而看懂 DeepTutor 为什么要求模型"第一行必须输出标签"这种设计。
> 3. 你会理解**幻觉、位置偏见、长文本遗忘**这些工程问题的物理来源，排错时不至于抓瞎。

## 2.2 第一步：词怎么变成数字

计算机不认字，只认数字。所以任何文本进模型前，都要先变成数字。

### 2.2.1 分词与查表

```text
"小明 把 书 放进 书包"
      │
      ▼  第一步: 分词 (tokenize) —— 第 5 章细讲
   [小明][把][书][放进][书包]
      │
      ▼  第二步: 查表, 每个词换成一串数字
   小明  → [0.21, -0.53, 0.88, ..., 0.04]   (比如 4096 个数字)
   把    → [0.10,  0.72, -0.31, ..., 0.55]
   书    → [-0.44, 0.19, 0.63, ..., 0.28]
   放进  → [0.33, -0.08, 0.14, ..., -0.71]
   书包  → [-0.40, 0.22, 0.59, ..., 0.31]
```

这一串数字叫**词向量（embedding）**。这张"词 → 数字"的对照表，是训练时学出来的，不是人定的。

### 2.2.2 词向量为什么有意义

关键在于：**意思相近的词，数字也相近**。

```text
把 4096 维压成 2 维画出来 (示意):

        猫 ●
     狗 ●   ● 兔子          ← 动物挤在一起
                                  桌子 ●
                                     ● 椅子    ← 家具挤在一起
   跑 ●
      ● 走
         ● 跳                ← 动作挤在一起
```

看上面例子里的"书"和"书包"，它们的数字确实比较接近（都跟阅读、物品相关），但不完全一样。这种"用位置表达含义"的思路是整个深度学习处理语言的基础。

> 直觉记法：**词向量把"语义"变成了"坐标"。** 意思接近 = 坐标接近，于是"判断两个词相不相关"就变成了"算两个坐标离得近不近"——而这是计算机最擅长的事。

## 2.3 自注意力：每个词回头看所有词

现在进入正题。

### 2.3.1 一句话版本

> 处理每一个词的时候，让它跟句子里所有词（包括自己）都算一个"相关性分数"，然后按分数把所有词的信息加权混合起来，作为这个词的新表示。

再翻译成人话：**"它"这个词，去问句子里每个词："我们俩有关系吗？"，得到一堆分数，然后按分数大小，把有关系的词的信息吸收进自己。**

### 2.3.2 用注意力矩阵看清楚

我们把"小明把书放进书包"这句话的注意力算出来（数字是示意，不是真实模型输出）。**行 = 谁在看，列 = 被看的词，数字 = 关注度，一行加起来等于 1**：

```text
              小明   把    书   放进  书包
            ┌──────────────────────────────┐
     小明   │ 0.62  0.08  0.11  0.10  0.09 │  主要看自己
      把    │ 0.31  0.24  0.28  0.12  0.05 │  连接主语和宾语
      书    │ 0.14  0.09  0.55  0.10  0.12 │  主要看自己
     放进   │ 0.28  0.06  0.33  0.19  0.14 │  看施事和受事
     书包   │ 0.09  0.04  0.21  0.19  0.47 │  也瞥了一眼"书"
            └──────────────────────────────┘
```

现在把句子改成有代词的版本，看"它"那一行：

```text
句子 A: 小明 把 书 放进 书包 因为 它 太重 了

              小明   把    书   放进  书包  因为   它   太重
            ┌────────────────────────────────────────────┐
      它    │ 0.03  0.01  0.58  0.04  0.19  0.02  0.08  0.05 │
            └────────────────────────────────────────────┘
                            ↑                    "它"死死盯着"书"
                          0.58

句子 B: 小明 把 书 放进 书包 因为 它 太空 了

              小明   把    书   放进  书包  因为   它   太空
            ┌────────────────────────────────────────────┐
      它    │ 0.03  0.01  0.15  0.04  0.61  0.02  0.09  0.05 │
            └────────────────────────────────────────────┘
                                        ↑      "它"改盯"书包"
                                      0.61
```

同一个"它"，因为后面的形容词不同，注意力自动转移到了不同的词上。**没有人写过任何一条"如果后面是'重'就指向'书'"的规则**——这是模型从海量文本里自己学出来的。

这就是 Transformer 强大的根源：**它学的不是词，是词与词之间的关系模式。**

## 2.4 Q / K / V：一个相亲角类比

论文里自注意力被写成 Query、Key、Value 三个东西。名字很吓人，其实是个非常朴素的**检索**比喻。

### 2.4.1 图书馆检索版

```text
你走进图书馆找资料:

  Query (查询)  = 你写在纸条上的需求: "我想找关于机器学习的书"
  Key   (索引)  = 每本书书脊上的标签: "机器学习" "唐诗" "菜谱"
  Value (内容)  = 每本书里真正的正文内容

  流程:
    1. 拿你的 Query 去和每本书的 Key 比对 → 得到相似度分数
    2. 分数高的书,多读一点; 分数低的书,少读一点
    3. 按分数加权,把所有书的 Value 混合成你最终的收获
```

在自注意力里，**每个词同时扮演三个角色**：

| 角色 | 这个词在干什么 | 类比 |
| --- | --- | --- |
| Query | 我想找什么样的词 | 我的检索需求 |
| Key | 我是什么样的词，谁该来找我 | 我的书脊标签 |
| Value | 如果你找到我，能从我这拿走什么信息 | 我的正文内容 |

同一个词的 Q、K、V 是三份不同的数字，由三组不同的、训练出来的权重从词向量变换而来。

### 2.4.2 完整数据流

```text
输入词向量
   │
   ├──► [W_q 变换] ──► Query  ─┐
   │                            ├──► Q 和 K 逐对比对 ──► 相关性原始分
   ├──► [W_k 变换] ──► Key    ─┘                            │
   │                                                        ▼
   │                                              缩放 + 归一化(softmax)
   │                                                        │
   │                                                        ▼
   └──► [W_v 变换] ──► Value ─────────────────────► 按注意力权重加权求和
                                                            │
                                                            ▼
                                                      这个词的新表示
```

"归一化"那一步做的事就是：把一堆乱七八糟的分数，压成一组加起来等于 1 的比例，也就是上面矩阵里那些 0.58、0.19。

### 2.4.3 为什么长文本这么贵

看这个结构你会发现一件事：**每个词都要和每个词比一次**。

```text
10 个词    → 10 × 10   = 100 次比对
100 个词   → 100 × 100 = 10000 次比对        长度 ×10, 计算 ×100
1000 个词  → 1000×1000 = 1000000 次比对      长度 ×10, 计算 ×100
```

**长度翻倍，计算量翻四倍。** 这就是"平方复杂度"，也是长上下文模型贵、慢、有上限的物理原因。

DeepTutor 在 `deeptutor/services/llm/context_window.py:8` 把可用窗口硬性封顶在 `MAX_EFFECTIVE_CONTEXT_WINDOW = 1_000_000`，并在 `context_window.py:10` 用一张 `KNOWN_LARGE_CONTEXT_MARKERS` 名单（含 `gpt-4o`、`claude`、`gemini`、`qwen`、`deepseek` 等）判断某个模型属不属于"大窗口家族"。这些工程决策的根，就在这个平方复杂度上。

> **提示 · 记住这条经验法则**
>
> 上下文不是"能塞就塞"。塞进去的每一个 token 都要和其他所有 token 做比对，代价是平方级的。**"少而准"永远优于"多而杂"**——这句话会贯穿第 5 章上下文工程和第 26 章记忆系统。

## 2.5 多头注意力：同时用多种视角看

真实的 Transformer 不是只算一组注意力，而是**并行算很多组**，叫**多头注意力（Multi-Head Attention）**。

为什么？因为词之间的关系有很多种，一组注意力表达不完：

```text
句子: 那只 黑色的 猫 昨天 在 院子里 抓 了 一只 老鼠

  头 1 (语法头):  "抓" ──► 主语"猫", 宾语"老鼠"
  头 2 (修饰头):  "猫" ──► "那只" "黑色的"
  头 3 (时间头):  "抓" ──► "昨天"
  头 4 (地点头):  "抓" ──► "院子里"
  ...
  头 32                 各自关注不同类型的关系

              ↓ 全部拼起来再变换一次 ↓

      "抓"这个词的最终表示,同时包含了
       谁抓的、抓了什么、什么时候、在哪
```

类比：**一个案子派 32 个侦探同时查，有人查动机，有人查时间线，有人查现场物证，最后开会汇总。** 比一个侦探什么都查要全面得多。

## 2.6 位置编码：Transformer 的先天缺陷与补丁

### 2.6.1 缺陷是什么

回头看 2.3 的注意力矩阵——它只关心"词和词的相关性"，**完全没有用到词的先后顺序**。

这意味着，如果不做任何处理：

```text
"狗 咬 人"  和  "人 咬 狗"
```

在 Transformer 眼里是**一模一样**的！因为参与计算的只是一组词向量的集合，顺序信息在"全部摊开并行处理"的那一刻就丢了。

这是 Transformer 为了换取并行能力付出的代价。RNN 天生有顺序（因为它就是一个一个读的），Transformer 没有。

### 2.6.2 补丁：给每个位置盖个戳

解决办法很直接：**在词向量里，额外加进一份"我在第几位"的信息**。这叫**位置编码（Positional Encoding）**。

```text
       词本身的含义        位置信息         送进注意力的最终输入
  狗:  [0.4, -0.2, ...]  +  [第0位的戳]  =  [0.4+p0, -0.2+p0', ...]
  咬:  [0.1,  0.7, ...]  +  [第1位的戳]  =  [0.1+p1,  0.7+p1', ...]
  人:  [0.9,  0.3, ...]  +  [第2位的戳]  =  [0.9+p2,  0.3+p2', ...]

  换成 "人 咬 狗":
  人:  [0.9,  0.3, ...]  +  [第0位的戳]  =  数字不同了!
  咬:  [0.1,  0.7, ...]  +  [第1位的戳]
  狗:  [0.4, -0.2, ...]  +  [第2位的戳]
```

同一个"狗"，在第 0 位和第 2 位，进入模型的数字就不一样了，顺序信息就此保留。

现代模型多用**旋转位置编码（RoPE）** 这类相对位置方案，好处是**外推性更好**——训练时只见过 4K 长度，推理时能勉强撑到更长。你会在模型发布说明里看到"通过 RoPE 扩展支持 128K 上下文"这种话，指的就是这件事。

> 工程含义：位置编码是"外推"出来的，不是"训练"出来的。所以**超长上下文的尾部质量往往会下降**——这是很多人观察到的"文档中间的内容模型看不见"（lost in the middle）现象的成因之一。

## 2.7 Encoder / Decoder：三种架构

Transformer 原始论文是为翻译设计的，有两半：Encoder（编码器）和 Decoder（解码器）。后来这两半被拆开单用，形成三个流派。

### 2.7.1 关键区别：能不能看见未来

```text
Encoder 的注意力 (双向, 可以看全文):

              我   爱   吃   苹果
       我   │ ✓    ✓    ✓    ✓  │
       爱   │ ✓    ✓    ✓    ✓  │   每个词都能看到所有词
       吃   │ ✓    ✓    ✓    ✓  │   包括自己后面的
      苹果  │ ✓    ✓    ✓    ✓  │


Decoder 的注意力 (单向/因果掩码, 只能看左边):

              我   爱   吃   苹果
       我   │ ✓    ✗    ✗    ✗  │
       爱   │ ✓    ✓    ✗    ✗  │   只能看到自己和左边
       吃   │ ✓    ✓    ✓    ✗  │   右边被"遮住"了
      苹果  │ ✓    ✓    ✓    ✓  │
```

Decoder 为什么要遮住右边？因为它的任务是**预测下一个词**。如果训练时能偷看答案，那就是作弊，学不到东西。这个遮罩叫**因果掩码（causal mask）**。

### 2.7.2 三种架构对照

| 架构 | 代表 | 能看见 | 擅长 | 一句话 |
| --- | --- | --- | --- | --- |
| 只用 Encoder | BERT | 全文双向 | 分类、抽取、检索 | 理解型，不会写 |
| 只用 Decoder | GPT / Claude / DeepSeek | 只看左边 | 生成、对话、写代码 | 生成型，当今主流 |
| Encoder + Decoder | T5、原始翻译模型 | 输入双向 + 输出单向 | 翻译、摘要 | 转换型 |

**今天你在 DeepTutor 里用到的模型，几乎全是 Decoder-only 架构。** 这不是巧合——Decoder-only 结构最简单、最好扩展，而且"预测下一个词"这个统一目标可以吃下所有任务。

### 2.7.3 这件事如何影响 DeepTutor 的设计

Decoder-only 只能从左往右生成，这个物理限制，直接塑造了 DeepTutor 的循环协议。

DeepTutor 要求模型在**回复的第一行**输出一个被双反引号包裹的标签（标签名如 FINISH、TOOL、THINK），程序据此决定这一轮该干什么。`deeptutor/core/agentic/labels.py` 的模块文档明确写着：*prompts require one allowed label, double-backtick-wrapped, on the first line of every reply*。解析函数是 `labels.py:33` 的 `classify_label`。

为什么标签必须在**第一行**？

```text
如果标签在最后:
   模型生成 500 字 ... 最后才说 "``TOOL``"
   → 程序必须等全部生成完才知道要调工具
   → 前面 500 字白流式输出了,用户干等

如果标签在第一行:
   模型刚吐出 "``TOOL``" (几个 token)
   → 程序立刻知道这轮是工具调用,马上切换处理逻辑
   → 后面的内容边生成边路由
```

这就是为什么 `deeptutor/core/agentic/labels.py:18` 定义了 `LABEL_PROBE_MAX_CHARS = 64`——只需要探测前 64 个字符，就能判定这一轮的走向，不必等全文。**因为模型只能从左往右生成，所以最重要的调度信息必须放在最左边。** 这是一个把模型物理特性直接翻译成工程设计的漂亮例子。

同样的道理也解释了流式：在 `deeptutor/core/agentic/labeled_step.py:487`，代码逐块读取 `delta.content` 并即时路由，正是因为 Decoder 是一个 token 一个 token 产出的。

## 2.8 把整个 Transformer 串起来

最后给你一张全景图。一层 Transformer Block 长这样，真实模型是几十层这样的块叠起来：

```text
                  输入: 词向量 + 位置编码
                          │
   ┌──────────────────────▼──────────────────────┐
   │  Transformer Block  (重复 N 层, N=32/80/...)  │
   │                                             │
   │   ┌─────────────────────────────────┐       │
   │   │   多头自注意力                    │       │
   │   │   (词与词交换信息)                │       │
   │   └────────────┬────────────────────┘       │
   │                │                            │
   │        残差连接 + 归一化                      │
   │        (把原输入加回来,防止信息丢失)            │
   │                │                            │
   │   ┌────────────▼────────────────────┐       │
   │   │   前馈网络 FFN                    │       │
   │   │   (每个词各自加工,不交换信息)      │       │
   │   │    ← 大部分参数其实在这里           │       │
   │   └────────────┬────────────────────┘       │
   │                │                            │
   │        残差连接 + 归一化                      │
   └────────────────┬────────────────────────────┘
                    │
                    ▼
            输出层: 算出词表里每个词的概率
                    │
                    ▼
            按概率抽样 → 下一个词 → 接回输入,再来一轮
```

两个补充说明：

- **残差连接**：把这一层的输入直接加到输出上。作用是"就算这一层什么都没学好，信息也不会丢"，这是能把网络堆到几十上百层的关键技巧。
- **前馈网络（FFN）**：注意力负责"词之间互相看"，FFN 负责"每个词单独加工消化"。有研究认为，模型的**事实性知识**主要存在 FFN 层里，注意力层更像是"路由器"。
