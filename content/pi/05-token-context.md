# 第 05 章 · Token、上下文窗口与上下文工程

> 如果说前四章讲的是"模型是什么"，这一章讲的是"你能给模型什么"。上下文是你和模型之间唯一的通道——模型不记得昨天，不知道你的项目，看不到你的屏幕。它只知道**这一次请求里你塞给它的那串 token**。把这串 token 组织好，是智能体开发中最核心、也最被低估的工程能力。

## 学习目标

- 理解 token 是什么，以及 BPE 分词的直觉
- 说清 `contextWindow` 和 `maxTokens` 的区别
- 知道上下文溢出会以什么形式发生、如何预防
- 建立"上下文工程"的整体框架
- 理解长对话为什么必须压缩，压缩又会损失什么

## 一、token：模型眼里的最小单位

### 1.1 为什么不用字符，也不用词

模型不能直接吃字符串，必须把文本切成离散单元再查表变成向量。切法有三种极端：

```text
按字符切：  "hello" → h, e, l, l, o
  优点：词表极小（几百个符号）
  缺点：序列超长，"国际化"三个字要 3 步，语义单元被打碎

按单词切：  "hello world" → hello, world
  优点：语义完整
  缺点：词表爆炸（英文几十万词，中文更糟），
        遇到没见过的词（新造词、拼错的词、变量名）直接歇菜

按子词切（BPE）：  "unhappiness" → un, happi, ness
  ← 折中方案，现代 LLM 的标准做法
```

### 1.2 BPE 的直觉

BPE（Byte Pair Encoding，字节对编码）的思路简单到可以手算：**从单个字符开始，反复把语料中最常一起出现的相邻单元合并成一个新单元**。

```text
初始语料（简化）：  low low low lower newest newest widest

第 1 步：统计相邻对频次
        "e" + "s" 出现最多 → 合并成 "es"
        newest → n e w es t

第 2 步：继续统计
        "es" + "t" 最多 → 合并成 "est"
        newest → n e w est

第 3 步：
        "l" + "o" → "lo"，然后 "lo" + "w" → "low"

...重复到词表达到设定大小（如 10 万）

最终结果：
  常见词  "low"     → 1 个 token
  较常见  "lower"   → "low" + "er" = 2 个 token
  罕见词  "xyzzy"   → 可能被拆成 4-5 个 token
```

**高频的东西占一个 token，低频的东西被拆碎**——这就是 BPE 的全部精髓。

### 1.3 一些必须有感觉的数字

| 内容 | 大致 token 数 |
| --- | --- |
| 1 个英文单词 | 约 1.3 个 |
| 1 个汉字 | 约 0.6～1.5 个（取决于分词器） |
| 100 字中文 | 约 100～150 个 |
| 一行普通代码 | 约 10～20 个 |
| 一个 500 行的源文件 | 约 5000～8000 个 |
| 一次典型的 `ls` 输出 | 几十到几百个 |
| 一份完整的 `package.json` | 约 500～2000 个 |

> **提示 · 分词器带来的真实怪癖**
>
> 很多"模型好蠢"的现象其实是分词造成的：
> - **数不清 strawberry 里有几个 r**：因为它看到的是 `straw` + `berry` 两个整块，字母层面的信息被吞掉了。
> - **大数运算容易错**：数字被切成不规则片段，`12345` 可能是 `123` + `45`，位值对齐被破坏。
> - **中文比英文更耗 token**：中文语料在多数分词器里占比偏低，很多常用词没能合并成单 token。
> 这些都不是"智力问题"，是**输入表示层的问题**。遇到这类任务，正确做法是给工具（计算器、脚本），而不是换提示词。

## 二、上下文窗口：一条硬边界

### 2.1 两个必须分清的数字

在 `packages/ai/src/types.ts` 的 `Model` 接口里，有两个相邻但含义完全不同的字段：

```ts
export interface Model<TApi extends Api> {
	// ...
	contextWindow: number;
	maxTokens: number;
	// ...
}
```

它们的关系用图最清楚：

```text
┌──────────────── contextWindow（如 200000）─────────────────┐
│                                                            │
│  ┌───────────────── 输入部分 ──────────────────┐ ┌────────┐│
│  │ 系统提示词 │ 历史消息 │ 工具定义 │ 工具结果 │ │ 输出   ││
│  └────────────────────────────────────────────┘ └────────┘│
│                                                   ▲        │
│                                          ≤ maxTokens       │
└────────────────────────────────────────────────────────────┘

contextWindow = 输入 + 输出 的总上限（一次请求里能容纳的全部 token）
maxTokens     = 单次回复最多能生成多少 token
```

关键推论：**输入越长，留给输出的空间越小**。如果你的输入已经占了 199000，而 `contextWindow` 是 200000，那模型最多只能回你 1000 个 token——哪怕 `maxTokens` 设成了 8192。

### 2.2 上下文里到底装了什么

很多人以为上下文就是"对话记录"。在智能体里远不止：

```text
一次真实的 Agent 请求，上下文构成：

┌────────────────────────────────────┐
│ 1. 系统提示词                       │  1000 ~ 5000 token
│    身份、规则、输出约定、环境信息    │  每轮都重复发送
├────────────────────────────────────┤
│ 2. 工具定义（JSON Schema）          │  1000 ~ 5000 token
│    每个工具的名称/描述/参数结构      │  工具越多越大
├────────────────────────────────────┤
│ 3. 项目上下文                       │  0 ~ 10000 token
│    项目说明文件、约定、技术栈        │
├────────────────────────────────────┤
│ 4. 对话历史                         │  随轮次线性增长
│    用户消息 + 助手回复 + 思考块      │
├────────────────────────────────────┤
│ 5. 工具执行结果                     │  ★ 增长最快的部分
│    文件内容、命令输出、搜索结果      │  一次读文件可能就上万
├────────────────────────────────────┤
│ 6. 本轮用户输入                     │  通常很小
└────────────────────────────────────┘
```

> **注意 · 第 5 项是绝大多数溢出的元凶**
>
> 用户输入通常只有几十个 token，但一次 `read` 大文件、一次 `npm install` 的完整日志、一次不加过滤的 `grep`，都可能瞬间灌进上万 token。**设计工具时必须给输出设上限并做截断**——这是编码智能体最重要的防御措施之一，第 29 章会看到 Pi 的具体做法。

## 三、上下文溢出：会发生什么

### 3.1 三种溢出形态

```text
形态 A · 请求被直接拒绝
  你发过去的输入超过了 contextWindow
  → API 返回 400，错误信息类似
    "This model's maximum context length is 200000 tokens,
     however you requested 213847 tokens"
  → 这是最好的情况：失败得明确

形态 B · 输出被中途截断
  输入没超，但输出写到一半撞上上限
  → 返回的 stopReason 是 "length" 而不是 "stop"
  → 表现为：代码写了一半、JSON 缺右括号
  → 危险，因为看起来像是"成功返回"

形态 C · 静默的质量下降
  在窗口内，但内容太长
  → 模型出现"中间遗忘"：对上下文开头和结尾记得清楚，
    中间部分的注意力显著变弱
  → 最危险，因为没有任何错误信号
```

Pi 用 `StopReason` 类型把第二种情况显式暴露出来：

```ts
export type StopReason = "pending" | "stop" | "length" | "toolUse" | "error" | "aborted" | "deferred";
```

看到 `"length"` 就要警惕——**这次回复是被硬切断的，不是模型说完了**。

### 3.2 「中间遗忘」值得单独说

研究和实践都反复观察到这个现象：把一条关键信息放在长上下文的不同位置，模型找到它的准确率呈 U 形分布。

```text
准确率
  高 │●                                    ●
     │ ●                                  ●
     │   ●                              ●
     │      ●                        ●
  低 │         ● ● ● ● ● ● ● ● ● ●
     └────────────────────────────────────────
      开头        中间部分          结尾
```

实用结论非常直接：

- **最重要的指令放系统提示词（开头）**
- **当前任务的关键信息放在最后**
- **不要指望模型仔细读中间那 10 万 token**

## 四、上下文工程：一门真正的工程

"提示词工程"关注怎么写好一段话；**上下文工程**关注的是——**在有限的窗口预算里，决定放什么、不放什么、以什么顺序放、放多久**。对智能体来说，后者重要得多。

### 4.1 它要解决的四个问题

```text
┌─────────────────────────────────────────────────┐
│  选择（Select）：这一轮该带哪些信息进上下文      │
│    · 用户提到的文件要，无关的 50 个文件不要      │
│    · 相关的历史轮次要，闲聊的轮次可以丢          │
├─────────────────────────────────────────────────┤
│  压缩（Compress）：装不下时怎么减                │
│    · 长文件只放相关片段                          │
│    · 老对话总结成摘要                            │
│    · 命令输出截断并注明"已省略 N 行"             │
├─────────────────────────────────────────────────┤
│  排序（Order）：什么放前面                       │
│    · 稳定内容在前（利于提示缓存命中）            │
│    · 关键任务信息靠后（避开中间遗忘）            │
├─────────────────────────────────────────────────┤
│  隔离（Isolate）：什么该单独处理                 │
│    · 子任务丢给独立的子智能体，只回收结论        │
│    · 大文件先摘要再进主上下文                    │
└─────────────────────────────────────────────────┘
```

### 4.2 顺序为什么影响成本

这一点很多人没意识到。回想第 02 章的 KV 缓存：前缀相同的部分可以复用计算结果。厂商据此提供"提示缓存"，命中缓存的 token 价格通常只有原价的一小部分。

```text
好的排列（前缀稳定）：
  [系统提示词][工具定义][项目说明] | [对话历史...][新消息]
   └──────── 每轮都一样 ────────┘   └─ 只有这里在变 ─┘
       ✓ 这一大段每轮都能命中缓存

坏的排列（前缀多变）：
  [当前时间戳][随机 ID][系统提示词][工具定义]...
   └─ 每轮都变 ─┘
       ✗ 第一个 token 就不同，整个缓存全部失效
```

这就是为什么 Pi 的 `Usage` 类型要单独统计缓存读写：

```ts
export interface Usage {
	input: number;
	output: number;
	cacheRead: number;
	cacheWrite: number;
	// ...
}
```

一条实操规则：**任何随请求变化的内容（时间戳、随机数、当前文件列表），都不要放在提示词最前面。** 第 12、24 章会详细讲缓存控制。

### 4.3 工具结果的处理策略

前面说了工具结果是溢出主因，这里给出四种常见的处理手法：

| 策略 | 做法 | 适用场景 |
| --- | --- | --- |
| 硬截断 | 超过 N 行就切，附注"已省略" | 命令输出、日志 |
| 分页 | 只返回一页，提供继续读取的参数 | 大文件读取 |
| 摘要化 | 用小模型先总结再入上下文 | 长文档、网页 |
| 引用化 | 只放路径和行号，需要时再读 | 搜索结果 |

> 一个好用的心法：**工具返回的应该是"决策所需的最小信息"，不是"我能拿到的全部信息"。** 判断标准很简单——如果这段内容模型看完不会改变下一步行动，它就不该占用上下文。

## 五、长对话为什么必须压缩

### 5.1 增长是不可逆的

智能体的上下文只增不减，而且增速远超直觉：

```text
轮次   本轮新增                    累计上下文
  1    系统提示 5k + 用户 0.1k      5.1k
  2    + 助手回复 0.5k + 工具结果 8k  13.6k
  3    + 0.5k + 12k（读了两个文件）  26.1k
  4    + 0.5k + 3k                  29.6k
  5    + 0.5k + 25k（跑了测试套件）  55.1k
  ...
 15    ...                          180k   ← 逼近 200k 上限
 16    ✗ 请求被拒绝
```

注意每一轮的**全部历史都要重发**。所以成本不是线性增长，而是接近平方级增长：第 n 轮要为前面 n-1 轮的所有内容再付一次钱。

### 5.2 压缩的基本思路

```text
压缩前（180k token）：
  [系统提示词]
  [轮次 1..12 的完整消息 + 所有工具结果]   ← 160k
  [轮次 13..15]                            ← 15k

压缩后（约 30k token）：
  [系统提示词]
  [★ 摘要：前 12 轮做了什么、结论是什么、
     当前状态如何、哪些文件已被修改]        ← 3k
  [轮次 13..15 保持原样]                    ← 15k
```

原则通常是：**远的压缩、近的保留、关键事实提取成结构化摘要**。

### 5.3 压缩一定会有损

必须诚实面对这一点。压缩会丢掉：

- **精确的代码内容**。摘要说"修改了 auth.ts 的过期判断"，但具体改成什么样了？没了。
- **失败的尝试**。"试过方案 A 但因为 X 失败"如果没写进摘要，模型可能再试一遍。
- **用户的隐含偏好**。第 3 轮用户说"我不喜欢用 class"，摘要里很可能不会记这句。

> **说明 · 压缩策略是有取舍的设计决策**
>
> 没有"最好的压缩"，只有"针对你的任务最合适的压缩"。编码智能体尤其需要保住这几类信息：
> 1. **已修改文件的清单**（避免重复修改或遗漏）
> 2. **用户明确表达过的约束**（技术选型、风格偏好）
> 3. **失败的路径**（避免鬼打墙）
> 4. **当前任务的目标状态**（避免跑偏）
> Pi 的压缩实现在 `packages/agent` 中，第 30 章会完整拆解它保留了什么、丢弃了什么、以及触发时机怎么定。

### 5.4 除了压缩还有别的办法

压缩是兜底手段，更好的策略是**从源头控制增长**：

```text
1. 工具输出限流       ← 最有效，成本最低
   读文件默认给范围，命令输出默认截断

2. 子智能体隔离
   "分析这 20 个文件" → 派给子智能体，只把结论 500 字带回来
   20 万 token 的工作，主上下文只花 500

3. 外部记忆
   把长期事实写进文件（如项目约定文档），
   需要时读取，而不是永久占着上下文

4. 主动开新会话
   任务切换时重开，比压缩干净得多
```

> 记住优先级：**别放进来 > 早点拿出去 > 压缩成摘要**。压缩是最后一道防线，不是第一选择。

## 六、动手估算一次真实请求

给你一个具体场景，自己算一遍会很有感觉。

```text
场景：让智能体给一个 300 行的 TypeScript 文件加单元测试

预估：
  系统提示词                     ~3,000
  工具定义（8 个工具）           ~2,500
  项目说明文件                   ~1,200
  用户消息                          ~30
  ─────────────────────────────────────
  首轮输入合计                   ~6,730

  轮 1：搜索测试目录 → 结果      ~400
  轮 2：读目标文件 300 行        ~4,000
  轮 3：读一个现有测试作参考      ~2,500
  轮 4：写测试文件（输出）        ~3,000
  轮 5：跑测试 → 输出            ~1,500
  轮 6：修复 → 输出              ~1,000
  ─────────────────────────────────────
  结束时上下文总量              ~19,000

结论：200k 窗口下非常宽裕。
但如果目标文件是 5000 行、测试套件输出 3 万行日志，
同样的任务会逼近 10 万 token —— 差距全在工具输出控制上。
```
