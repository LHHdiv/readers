# 第 06 章 · 提示词工程与系统提示词

> 提示词工程有点尴尬：一方面它被吹成"新时代的编程语言"，另一方面很多人觉得它就是"会说话"。真相在中间——对单次问答，它确实只是技巧；但对智能体，**系统提示词是产品的核心资产**，它定义了这个智能体是谁、能做什么、什么时候该停下来问你。这一章把技巧和工程分开讲。

## 学习目标

- 分清 zero-shot / few-shot，知道各自什么时候用
- 理解系统提示词在架构中的特殊地位
- 掌握消除歧义的具体手法
- 能可靠地拿到结构化输出
- 通过好坏对照建立自己的判断力
- 知道智能体的系统提示词和聊天机器人的提示词有什么本质不同

## 一、提示词到底在做什么

先破除一个误解：提示词不是"命令"模型，而是**在模型学到的概率分布上做条件约束**。

```text
模型内部有一个巨大的可能性空间：
  ┌──────────────────────────────────────────┐
  │  所有它能生成的文本                       │
  │   · 儿童故事    · 学术论文                │
  │   · 垃圾邮件    · Python 代码             │
  │   · 中文诗歌    · 客服对话                │
  └──────────────────────────────────────────┘

提示词的作用 = 把生成范围收缩到某个子区域

  "你是一位资深 Python 工程师，请用类型注解写代码"
        ↓
  ┌──────────────┐
  │ 带类型注解的  │   ← 生成就在这个小圈里采样
  │ 专业 Python   │
  └──────────────┘
```

这个视角能解释很多现象：

- **为什么给角色有用**：它把分布收缩到了"专业人士写的文本"那一区。
- **为什么举例子最有效**：例子直接展示了目标区域的样本，比任何描述都精确。
- **为什么否定句常常失效**："不要用 emoji"这句话里就有 emoji 这个概念，反而激活了它。正面表述"使用纯文本输出"更可靠。

## 二、zero-shot 与 few-shot

### 2.1 zero-shot：只说要求

```text
把下面的句子翻译成英文：今天天气真好。
```

不给任何示范，靠模型自己理解任务。**现代强模型在常见任务上 zero-shot 已经够用**，这是 few-shot 使用频率下降的原因。

### 2.2 few-shot：给几个样例

```text
把用户反馈分类为 bug / feature / question：

输入：点击保存按钮后页面白屏了
输出：bug

输入：希望能支持导出 PDF
输出：feature

输入：请问会员和普通用户有什么区别
输出：question

输入：登录时验证码一直收不到
输出：
```

few-shot 真正的价值不在"教会任务"，而在**锁定输出格式和判断边界**。上面的例子里，模型学到的其实是三件事：只输出一个词、用小写、这三个类别的具体分界线在哪。

### 2.3 什么时候该用哪个

| 情况 | 选择 | 原因 |
| --- | --- | --- |
| 常见任务（翻译、摘要、改写） | zero-shot | 模型早就会，给例子是浪费 token |
| 输出格式有严格要求 | few-shot | 例子比描述精确得多 |
| 分类边界模糊、有主观性 | few-shot | 用例子划定边界 |
| 需要模仿特定风格 | few-shot | 风格难以言传 |
| 有大量长例子 | 考虑微调 | 每轮都塞例子太贵 |
| 任务简单但你不放心 | zero-shot + 一个反例 | 只针对易错点给例子 |

> **提示 · few-shot 的三条实操细节**
>
> 1. **例子要覆盖边界情况**，特别是容易搞错的那类。只给简单例子等于没给。
> 2. **例子的分布会被模仿**。如果三个例子全是 `bug`，模型会倾向于把新输入也判成 bug。
> 3. **例子的格式必须完全一致**。你在示范里换了一次分隔符，输出格式就会开始漂移。

## 三、系统提示词：不只是"第一条消息"

### 3.1 它特殊在哪

技术上，系统提示词最终也是被拼进同一个 token 序列的（第 02 章讲过，Decoder-only 模型眼里没有本质区别）。但它有三重特殊性：

```text
1. 训练层面的特殊
   SFT 阶段专门训练了"system 角色的内容优先级更高"
   → 模型倾向于在冲突时服从系统提示词

2. 位置层面的特殊
   它永远在序列最前面
   → 利于提示缓存命中（第 05 章）
   → 避开了"中间遗忘"的注意力低谷

3. 生命周期的特殊
   用户消息一轮一条，系统提示词贯穿整个会话
   → 它定义的是"恒定规则"，不是"当前任务"
```

### 3.2 该往里放什么

一个成熟的智能体系统提示词，通常包含这六块：

```text
┌──────────────────────────────────────────────┐
│ 1. 身份与职责                                 │
│    你是什么、主要解决什么问题                  │
├──────────────────────────────────────────────┤
│ 2. 能力与边界                                 │
│    有哪些工具、什么事不做、什么事要先问        │
├──────────────────────────────────────────────┤
│ 3. 行为准则                                   │
│    改代码前先读、破坏性操作要确认              │
├──────────────────────────────────────────────┤
│ 4. 输出约定                                   │
│    简洁程度、代码风格、是否解释               │
├──────────────────────────────────────────────┤
│ 5. 环境信息                                   │
│    操作系统、工作目录、可用命令、当前时间      │
├──────────────────────────────────────────────┤
│ 6. 项目上下文                                 │
│    技术栈、项目约定（通常从文件动态注入）      │
└──────────────────────────────────────────────┘
```

前四块是**静态**的，后两块是**动态**的。这个划分不是为了整齐——它直接对应缓存策略：静态部分放前面稳定不变，动态部分放后面。Pi 的系统提示词构建就是这样组织的，第 36 章会看到它如何把这些片段拼装起来。

### 3.3 智能体提示词与聊天提示词的本质区别

这是很多人从"写 ChatGPT 提示词"转到"写智能体"时最大的认知落差。

| 维度 | 聊天机器人 | 智能体 |
| --- | --- | --- |
| 输出对象 | 给人看 | 一部分给机器解析 |
| 一次交互 | 一问一答 | 多轮循环，可能几十步 |
| 错误代价 | 答错了重问 | 可能改坏文件、执行危险命令 |
| 提示词重点 | 内容质量、语气 | **何时调工具、何时停、何时问用户** |
| 关键约束 | 别胡说 | **别乱做** |

所以智能体系统提示词里，**流程控制类的规则占比远高于内容质量类的规则**。举例：

```text
聊天机器人会写：
  "回答要专业、准确、有条理。"

智能体必须写：
  "修改任何文件前，必须先读取该文件的当前内容。
   执行会产生副作用的命令前，先说明你要做什么。
   如果用户的需求存在多种合理解释，先提问，不要猜。
   任务完成后不要主动扩展需求。"
```

> **注意 · 提示词不是安全边界**
>
> 再强调一次第 03 章的结论：写"不要删除用户文件"是**行为倾向引导**，不是**保障**。真正的保障必须是代码——工具层的路径校验、命令白名单、用户确认弹窗。提示词是第一层软防护，权限系统才是硬防护。

## 四、消除歧义：最值得练的基本功

模型的绝大多数"不听话"，其实是提示词本身有歧义。下面是四类常见歧义和修法。

### 4.1 程度词歧义

```text
✗ 差："请简洁地回答"
     ← "简洁"是 20 字还是 200 字？

✓ 好："用不超过三句话回答，不要开场白和总结句。"
```

### 4.2 范围歧义

```text
✗ 差："优化这段代码"
     ← 优化性能？可读性？内存？要不要改接口？

✓ 好："优化这段代码的可读性，保持函数签名和外部行为不变，
      不要引入新的依赖。"
```

### 4.3 结构歧义

```text
✗ 差："给我一个用户信息的 JSON"
     ← 字段叫什么？嵌套结构？日期什么格式？

✓ 好："返回 JSON，结构如下：
      { "id": number, "name": string, "createdAt": "YYYY-MM-DD" }
      不要包裹在代码块外的任何文字里。"
```

### 4.4 判断标准歧义

```text
✗ 差："如果代码有问题就修复"
     ← "有问题"的标准是什么？风格算问题吗？

✓ 好："只修复会导致运行时错误或逻辑错误的问题。
      代码风格、命名、注释缺失不算问题，不要动。"
```

> 一个自检办法：**把你的提示词给一个不了解背景的同事看，问他"你会怎么做"。** 如果他的理解和你的预期有偏差，模型也会偏。人类会靠常识补全歧义，模型不一定补成你想要的那个。

## 五、结构化输出

智能体经常需要机器可解析的输出。可靠性从低到高有四档做法。

### 5.1 档次一：只在提示词里要求（不推荐）

```text
请以 JSON 格式返回结果。
```

模型大概率会给你这样一坨东西：先来一句"好的，这是您需要的 JSON："，然后是一个带 `json` 标注的 Markdown 代码块围栏，里面才是 `{ "name": "张三" }`，最后再补一句"希望对您有帮助！"。

前后都是废话，中间还裹着围栏。你得写一堆字符串处理去剥，而且模型哪天心情一变，剥的规则就失效了。

### 5.2 档次二：给出精确 schema 和禁止项

```text
返回一个 JSON 对象，且只返回 JSON 本身。

字段定义：
- name: string，用户姓名
- age: number，整数年龄
- tags: string[]，标签数组，可以为空数组

严格要求：
- 不要输出 Markdown 代码块围栏
- 不要输出任何解释性文字
- 所有字段都必须存在，未知值用 null
```

明显更可靠，但仍然是"祈祷模型配合"。

### 5.3 档次三：用函数调用 / 工具调用

这是**质变**。不再让模型"写一段看起来像 JSON 的文本"，而是通过 API 的工具调用机制，让模型填一个有 JSON Schema 约束的参数结构。

```json
{
  "name": "extract_user",
  "description": "从文本中提取用户信息",
  "parameters": {
    "type": "object",
    "properties": {
      "name": { "type": "string", "description": "用户姓名" },
      "age": { "type": "number", "description": "整数年龄" },
      "tags": { "type": "array", "items": { "type": "string" } }
    },
    "required": ["name", "age"]
  }
}
```

好处是结构由协议层保证，很多厂商还支持**约束解码**——在生成时就限制只能产出符合 schema 的 token，从根本上杜绝格式错误。这是第 07 章的主题，也是整个智能体能力的基石。

### 5.4 档次四：加一层校验和重试

即便用了工具调用，也要在代码里做最终校验：

```ts
// 思路示意
const parsed = schema.safeParse(toolCall.arguments);
if (!parsed.success) {
	// 把校验错误作为工具结果回传给模型，让它自己修正
	return { error: `参数校验失败：${parsed.error.message}` };
}
```

**把错误信息回传给模型让它重试**，比在代码里猜它想说什么有效得多。Pi 在工具执行流水线里就是这么做的（第 28 章）。

> **说明 · 一条降低难度的原则**
>
> **能让结构简单就别复杂。** 三层嵌套的对象数组，模型出错率远高于扁平结构。如果一次拿不准，就拆成两次调用。为模型降低任务难度，永远比事后修补划算。

## 六、好坏对照集

下面每组都是真实场景里高频出现的问题。

### 6.1 角色设定

```text
✗ 坏：
你是世界上最顶尖的、无所不能的 AI 编程大师，
拥有 30 年经验，精通所有编程语言，能解决任何问题！

✓ 好：
你是一个 TypeScript 后端开发助手。你熟悉 Node.js 生态、
REST API 设计和 PostgreSQL。当问题超出这些范围时，
明确说明你的不确定性。
```

问题在于：夸张的形容词不会提升能力，只会提升**自信程度**——模型更倾向于对不懂的事情硬答。**给具体领域，并明确要求承认不确定性**，才是有效的角色设定。

### 6.2 任务描述

```text
✗ 坏：
帮我看看这个函数有没有问题。

✓ 好：
审查下面的函数，重点检查三项：
1. 边界条件（空数组、null、超长输入）
2. 异步错误处理是否完整
3. 是否有资源泄漏

按「问题 → 影响 → 建议改法」的格式列出发现的问题。
如果某一项没有问题，就写"无"。
```

### 6.3 输出控制

坏的写法是"详细解释一下这段代码"——"详细"是最危险的词之一，它会换来三千字的逐行注释。好的写法把量和内容都框死："用不超过 5 行说明这段代码解决什么问题、有什么前置条件，不要逐行翻译代码。"

### 6.4 约束表达

```text
✗ 坏：
不要修改其他文件，不要添加注释，不要改变格式，
不要引入新依赖，不要重构，不要...

✓ 好：
本次修改的范围：只修改 src/auth.ts 中的 validateToken 函数体。
其余一切保持原样。
```

一长串否定句既占 token 又容易漏，而且否定表述本身对模型不友好。**用一句正面的范围界定，替换十句禁令。**

### 6.5 处理不确定性

```text
✗ 坏：
（什么都不说，默认模型会问）

✓ 好：
如果实现方式存在多种合理选择（比如用配置文件还是环境变量），
先列出选项和各自的取舍，等我确认后再动手。
不要自行决定后直接实现。
```

智能体最容易出的问题不是做错，而是**没问就做**。这条规则必须显式写。

## 七、迭代提示词的方法

提示词不是一次写对的，它是调出来的。给一个可操作的流程：

```text
1. 先写最小版本 —— 别一上来写 500 行，写 30 行先跑起来
2. 收集失败案例 —— 存原始输入输出，别只记"它有时会出错"
3. 归类失败原因
   ├─ 歧义类  → 补充精确定义
   ├─ 格式类  → 加例子或改用工具调用
   ├─ 越界类  → 加范围约束
   └─ 能力类  → 提示词救不了，换模型或给工具
4. 每次只改一处 —— 同时改三条，你不知道是哪条起的作用
5. 回归验证 —— 用全部历史失败案例重跑
   ★ 提示词修改经常"修好一个、弄坏两个"
```

> **提示 · 提示词也需要版本管理**
>
> 把系统提示词当代码对待：放进仓库、写变更说明、保留失败案例集当作测试用例。Pi 把系统提示词作为独立资源来组织和构建（第 36 章），而不是散落在代码里的字符串拼接——这正是"提示词是资产"这个认知的工程体现。

## 八、与后续章节的衔接

这一章讲的是**怎么写**，后面几章讲的是**怎么组织和构建**：

- 第 07 章：函数调用与工具定义——工具的 `description` 本身就是提示词的一部分，写得好不好直接决定模型会不会正确使用它。
- 第 36 章：Pi 如何构建系统提示词——静态片段、动态环境信息、项目文件注入是怎么拼装的，以及为什么这样切分。
- 第 38 章：技能系统——把领域知识做成可按需加载的提示词模块，避免一次性把所有知识塞进系统提示词。

> 一个提前打的预防针：**系统提示词不是越长越好**。它每轮都要重发，直接占用窗口和成本；过长还会稀释关键指令的权重。真正成熟的做法是**分层加载**——核心规则常驻，领域知识按需注入。这就是技能系统存在的理由。
