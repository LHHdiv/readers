# 第 08 章 · 智能体范式：ReAct、Plan-and-Execute、反思循环

## 8.1 什么是"智能体"（Agent）

前面几章我们拆了 prompt、模型、工具调用。把它们**串起来自动跑**，就是一个智能体。给个更正式的说法：

> 智能体 = 能**感知**环境、**决策**下一步动作、**执行**动作，并根据结果**更新自身状态**，如此循环直到任务完成的程序。

用生活类比：你让一个实习生"把线上 bug 修掉"。他不会一上来就瞎改代码，而是先**看**（读报错、读相关文件），再**想**（哪里出问题、怎么改），再**做**（改文件、跑测试），看完测试结果再决定下一步。这个"看—想—做—看"的循环，就是智能体的灵魂。

> **提示 · 智能体 vs 普通程序**
>
> 普通程序：你写死每一步（`if x then y`）。
> 智能体：你只给目标，每一步"想不想调工具、调哪个"由模型临场决定。把"控制流"交给了 LLM。

Pi 仓库版本为 `0.0.3`，其智能体运行时的核心就是这个循环，实现在 `packages/agent/src/agent-loop.ts`（入口函数 `agentLoop`），它在 `Context` 上反复跑"调用模型 → 执行工具 → 回填"直到结束。

## 8.2 Agent Loop：所有范式的共同骨架

不管下面哪种范式，底层都是同一个循环。先建立骨架，再往里填"思考方式"的差异：

```text
        ┌─────────────────────────────────────┐
        │                                     │
        ▼                                     │
   ① 感知/读取上下文 (Context)                  │
        │                                     │
        ▼                                     │
   ② 模型决策：输出文本 or tool_call            │
        │                                     │
        ▼                                     │
   ③ 若 tool_call：宿主执行工具                 │
        │         得到结果                     │
        ▼                                     │
   ④ 回填 ToolResultMessage ───────────────────┘
        │
        ▼
   ⑤ 若模型 stop：把答案交给用户，结束
```

第 7 章讲过，`toolUse` 触发循环继续，`stop` 触发结束。下面三种范式，区别只在于"模型在 ② 里怎么想"。

## 8.3 ReAct：推理与行动交替

**ReAct** = **Re**asoning + **Act**ing，是 2022 年提出、至今最主流的范式。核心思想：让模型把"内心嘀咕"（推理）和"动手动作"（行动）**交替写在同一段输出里**，形成可追踪的链路。

一个 ReAct 回合长这样（伪代码风格）：

```text
Thought: 用户要我修登录 bug。先看看报错日志在哪个文件。
Action: read_file(path="src/login.ts")
Observation: （工具返回文件内容）
Thought: 第 42 行 try/catch 吞了异常，导致错误没抛出。我应该补一个 throw。
Action: edit_file(path="src/login.ts", ...)
Observation: （修改成功）
Thought: 改完了，跑一下测试确认。
Action: run_tests()
Observation: 全部通过。
Thought: 任务完成，可以回复用户了。
Answer: 已修复 src/login.ts 第 42 行……
```

> **说明 · 为什么 ReAct 有效**
>
> 模型"边想边做"会把中间推理显式写出来，既方便你 debug（能看到它哪步想歪了），也降低"一口气答错"的概率。Pi 这类 coding agent 基本就是 ReAct 的实装：每轮模型先产出思考/文本，再产出 `ToolCall`，宿主执行后把 `Observation` 回填。

下面用 ASCII 画出 ReAct 循环：

```text
用户目标
   │
   ▼
┌─────────────── ReAct 循环 ───────────────┐
│                                          │
│   Thought（模型内心推理，文本）           │
│      │                                   │
│      ▼                                   │
│   Action（tool_call：要调哪个工具）       │
│      │                                   │
│      ▼                                   │
│   ┌─────────┐                            │
│   │ 宿主执行 │                           │
│   └─────────┘                            │
│      │                                   │
│      ▼                                   │
│   Observation（工具结果回填）             │
│      │                                   │
│      └──────────── 回到 Thought ──────────┘
│                  （直到模型不再 Action）   │
└──────────────────────────────────────────┘
   │
   ▼
最终 Answer → 用户
```

## 8.4 Plan-and-Execute：先规划，再一步步执行

ReAct 有个毛病：任务一长，模型容易"走一步看一步"最后迷路。于是有了 **Plan-and-Execute**：

- **Plan 阶段**：先让模型把整个任务拆成一串步骤（一份计划清单）。
- **Execute 阶段**：按计划**逐步**执行，每步可以是一个小 ReAct 子循环。

```text
任务：给项目加一个用户注册功能
   │
   ▼
Plan（模型输出）:
  1. 建数据库表 users
  2. 写注册 API 路由
  3. 写前端表单
  4. 加单元测试
   │
   ▼
Execute 第 1 步（内部可用 ReAct 小循环）
Execute 第 2 步
Execute 第 3 步
Execute 第 4 步
   │
   ▼
完成
```

好处：大任务有"总纲"，不容易跑偏；坏处：计划可能过时（执行到第 3 步发现第 2 步设计错了），需要"计划重排"机制。很多高级 coding agent 会混用两种：顶层 Plan，底层 ReAct。

## 8.5 Reflection：反思 / 自我批评

模型第一版答案常常不完美。**Reflection（反思）**范式让模型在产出后**自己审查自己**：

```text
① 模型生成初版答案/方案
② 模型切换"评审视角"：这版有什么问题？漏了啥？错在哪？
③ 把"批评意见"作为新上下文，让模型改一版
④ 重复 ② ③ 直到满意（或达到次数上限）
```

> 类比：你写完代码先自己 code review 一遍再提交。Reflection 就是把"自我审阅"做进循环。

Reflection 常和其他范式叠加：ReAct 跑完一轮，再 Reflection 一下"我刚才那几步合理吗"，不合理就重来。代价是**多花 token、多一轮延迟**——是否值得，要看任务容错率。

> **提示 · 人在回路（Human-in-the-loop）**
>
> Reflection 是"模型审模型"。更稳的是"人审模型"：在关键节点（比如要删库、要发钱）暂停，等真人点"继续/取消"。Pi 的 README（`README.md:40`）明确说：Pi 默认不内置权限系统，以启动它的用户权限运行；要强边界就容器化/沙箱。也就是说"人在回路"的把关，往往落在你部署时的沙箱策略上，而非模型循环里。

## 8.6 三种范式对比

| 范式 | 核心思路 | 适合场景 | 主要代价 |
|------|----------|----------|----------|
| ReAct | 推理与行动交替 | 交互式、需随时查环境的任务 | 长任务易跑偏 |
| Plan-and-Execute | 先总规划再分步执行 | 大任务、多步骤项目 | 计划可能过时 |
| Reflection | 生成后自我批评再改 | 容错低、质量要求高 | 多一轮 token 与延迟 |

## 8.7 这些范式如何映射到 Pi 的 agent-loop

Pi 的 `packages/agent/src/agent-loop.ts` 提供的是**通用循环骨架**（`agentLoop` / `agentLoopContinue`），它本身不绑定某一种"思考风格"——思考风格由你放进 `Context.systemPrompt` 的指令和可用工具决定：

- 想做 **ReAct**：系统提示写"先 Thought 再 Action"，工具集给文件/命令类工具，循环自然成 ReAct。
- 想做 **Plan-and-Execute**：用一个"规划工具"先产出计划文本，再逐个 step 调用执行工具。
- 想做 **Reflection**：在工具集里放一个"自我评审"步骤，或在宿主层多跑一轮让模型审阅自己的 `AssistantMessage`。

> 本书后续"第 25 章"会深入 Pi 的 `agent-loop` 实现细节（事件流 `AgentEvent`、如何 `convertToLlm` 把 `AgentMessage` 转成 `Message[]` 再边界调用模型）。本章你只需记住：**范式是"思考方式"，agent-loop 是"跑思考方式的发动机"**，二者解耦。

> **说明 · 解耦的好处的直觉**
>
> 因为循环和思考风格解耦，Pi 换模型（DeepSeek/OpenAI/Anthropic）或换范式时，不用重写循环引擎——只要换 `Context` 里的提示词和工具。这正是"统一多供应商 LLM API"（`packages/ai`）存在的意义。

## 8.8 三种范式的常见陷阱

- **ReAct 无限循环**：模型反复调同一个工具却不停（比如一直 `grep` 同一个词）。要在宿主层加"最大步数"上限，到顶就强制收尾。
- **Plan-and-Execute 计划僵化**：执行到第 3 步发现第 1 步的计划错了，却硬着头皮走。进阶做法是"动态重规划"——每几步重新评估一次计划。
- **Reflection 自欺**：模型自我批评时只说好话、不真挑刺。可要求它"先列出 3 个可能错的地方"来强制批判性。

```text
防呆机制（宿主层加）：
  ├─ max_steps：单轮最多调 N 次工具
  ├─ budget：token / 钱 上限
  └─ guardrail：危险动作（删库/发钱）必须人工确认
```

## 8.9 在 coding agent 里看这三种范式

把抽象范式落回"改代码"的具体动作，会更踏实：

| 范式 | coding agent 中的样子 |
|------|----------------------|
| ReAct | 读报错 → 想根因 → 改文件 → 跑测试 → 看结果再决定下一步 |
| Plan-and-Execute | 先列出"修复计划 1/2/3 步"，再逐 step 用 ReAct 小循环执行 |
| Reflection | 改完一轮后，让模型以 reviewer 视角审自己的 diff，挑刺后再改一版 |

Pi 的 `agent-loop`（`packages/agent/src/agent-loop.ts:31`）不限制你用哪种——它只保证"模型输出 → 执行工具 → 回填 → 再循环"这个引擎稳定转。思考风格全在你给的提示词和工具集里。这和第 10.5 节 Pi 的"极简内核 + 扩展点"哲学一脉相承：**发动机通用，个性留给上层配置**。

> **说明 · 一个反直觉的事实**
>
> 最实用的生产级 coding agent，往往不是"纯 ReAct"或"纯 Plan"，而是**混合**：顶层用轻量 Plan 给方向，底层每步用 ReAct，关键改动前插一道 Reflection/人工确认。范式不是单选，是拼装。

## 8.10 范式选择决策树

面对一个任务，怎么选范式？给个直觉决策流程：

```text
任务复杂吗？
  ├─ 简单、一步到位 ──────────────▶ 不用 agent，直问模型
  └─ 复杂、要查环境/动手
        │
        ├─ 步骤清晰、能先列计划？ ──▶ Plan-and-Execute（先规划）
        │     └─ 计划可能中途变？ ──▶ 加"动态重规划"
        ├─ 步骤模糊、需边走边看？ ──▶ ReAct（默认首选）
        └─ 质量要求极高、错不起？ ──▶ 在以上任一种后加 Reflection
              └─ 涉及危险动作？ ─────▶ 再加 Human-in-the-loop 把关
```

多数 coding agent 的**默认起点是 ReAct**：因为改代码天然是"看—想—做"交替。等任务规模上来，再叠加 Plan 和 Reflection。别一上来就堆最复杂的组合——复杂度本身也是成本。

## 8.11 范式与"工具调用"的衔接点

回顾第 7 章：工具调用的闭环是"模型输出 tool_call → 宿主执行 → 回填 ToolResultMessage"。三种范式其实都**建立在这个闭环之上**，区别只在"模型在输出 tool_call 前怎么组织思路"：

```text
ReAct    ：每轮都允许"先想一句再出一个 tool_call"
Plan     ：先用一个特殊的"规划输出"定好步骤，再逐 step 走工具闭环
Reflection：工具闭环跑完后，额外走一轮"评审输出"再决定改不改
```

所以学范式的正确姿势是：先把第 7 章的工具闭环吃透，范式只是"在闭环外面包了不同的思考包装纸"。Pi 的 `agent-loop` 提供的是那张纸下面的发动机，思考包装由你的 `systemPrompt` 决定——这是同一套机制的两层抽象。

> **说明 · 一个常见误解**
>
> 有人以为"ReAct / Plan-and-Execute 是某种特殊 API 或框架类"。不是。它们是**提示词 + 循环控制**的模式，不是新接口。你用同一套 `ToolCall`/`ToolResultMessage`，换提示词就能从 ReAct 变 Plan。理解了这点，范式就不可怕了。

## 8.12 本章关键点回顾

- 智能体 = 感知—决策—行动—更新的自动循环。
- ReAct 把推理和行动交替写出，最主流；Plan-and-Execute 先规划后执行；Reflection 自我批评再改。
- 人在回路是把关手段，Pi 把它放在部署层（沙箱）而非循环层。
- Pi 的 agent-loop 是范式无关的发动机，范式由 systemPrompt + 工具决定。

## 8.13 范式速记口诀

最后用三句话把三种范式钉进记忆：

- **ReAct**：想一步、做一步，边走边看——coding agent 的默认姿势。
- **Plan-and-Execute**：先画地图再出发，适合大任务防迷路。
- **Reflection**：做完自己审一遍，质量换成本。

记住：**范式是"思考包装纸"，agent-loop 是"发动机"，工具调用是第 7 章那张"便条"**。三层叠起来，才是一个能动手的智能体。
