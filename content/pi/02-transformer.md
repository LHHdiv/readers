# 第 02 章 · Transformer 与注意力机制直觉

> 你不需要会推导 Transformer 就能写智能体，但你**必须**知道它是怎么工作的。因为它的结构直接决定了：为什么有上下文窗口上限、为什么长对话越来越贵、为什么模型能"记住"你十轮前说的话、以及为什么流式输出是一个 token 一个 token 蹦出来的。这一章用图和比喻讲清楚，全程不出现一个求和符号。

## 学习目标

- 说清 Seq2Seq 的两个致命瓶颈
- 用"图书馆检索"的比喻讲明白 Query / Key / Value
- 理解多头注意力为什么要"多头"
- 知道位置编码解决的是什么问题
- 说清 Encoder-Decoder 与 Decoder-only 的区别，以及为什么 LLM 选了后者
- 理解为什么训练能并行、推理却只能一个个吐字

## 一、从上一章的断点接上

第 01 章结尾我们停在这里：Seq2Seq 用一个固定向量传递整句话的语义，撞上了两堵墙。

```text
瓶颈 A · 信息压缩
   "我昨天在城东那家新开的川菜馆点了一份很辣的水煮鱼"
                        ↓ 压成一个 512 维向量
                    [0.13, -0.88, ... ]
                        ↓ 解码
   丢掉了什么？大概率是"城东""昨天"这类细节

瓶颈 B · 无法并行
   h1 → h2 → h3 → h4 → h5
   算 h5 必须先算完 h4，GPU 上万个核心大部分在闲置
```

Transformer 的答案是：**两个瓶颈用同一个机制一起解决——自注意力（self-attention）**。

## 二、自注意力的直觉：图书馆检索

先别看公式。想象你在图书馆找资料。

- 你手里有一个**检索需求**，比如"关于宋代茶文化的资料"——这是 **Query（查询）**。
- 每本书的书脊上有**标签**，比如"宋史""茶经""明代瓷器"——这是 **Key（键）**。
- 每本书的**正文内容**才是你真正想要的——这是 **Value（值）**。

检索过程：拿你的 Query 去和每一个 Key 比相似度，越像的书给越高的权重，然后**按权重把所有书的内容混合起来**，得到你要的答案。

```text
Query: "宋代茶文化"
   │
   ├── 比对 Key "宋史"        → 相似度 0.6
   ├── 比对 Key "茶经"        → 相似度 0.9
   ├── 比对 Key "明代瓷器"    → 相似度 0.1
   └── 比对 Key "机械制图"    → 相似度 0.0
   │
   ▼  归一化成权重（softmax）
   0.30 × Value(宋史) + 0.62 × Value(茶经) + 0.07 × Value(瓷器) + 0.01 × ...
   │
   ▼
 融合后的新表示
```

### 2.1 "自"注意力的含义

上面是"我去查别人"。**自**注意力的特别之处在于：**句子里的每个词，同时扮演 Query、Key、Value 三个角色，互相检索**。

```text
句子： 那只 猫 因为 太累 了 所以 它 没有 跳 上 沙发

处理 "它" 这个词时：
  "它" 发出 Query：我指代谁？
   ├─ Key "猫"   → 0.71   ← 高度相关
   ├─ Key "沙发" → 0.12
   ├─ Key "太累" → 0.09
   └─ 其余       → 0.08
  
  结果："它" 这个位置的新向量里，混入了 71% 的"猫"的语义
```

**这就是模型"理解"上下文的方式**：每个词的表示都被它关注到的其他词重塑过一遍。同一个"它"，在不同句子里会得到完全不同的向量。

> **提示 · 这是全书最值得记住的一张图**
>
> "每个 token 都去看其他所有 token，按相关度加权融合"——一句话概括自注意力。后面所有关于上下文、成本、窗口限制的讨论，都能从这句话推出来。

### 2.2 Q / K / V 从哪来

每个词先被转成一个向量（词嵌入），然后乘以三个不同的权重矩阵，得到三份不同的"人格"：

```text
                    ┌──▶ × W_Q ──▶ Query  （我在找什么）
词向量 x ───────────┼──▶ × W_K ──▶ Key    （我能提供什么）
                    └──▶ × W_V ──▶ Value  （我的实际内容）
```

`W_Q` / `W_K` / `W_V` 是训练学出来的参数。**同一个词，作为"提问者"和作为"被查者"，用的是不同的表示**——这个设计让模型能表达非对称关系，比如"修饰"和"被修饰"。

### 2.3 完整流程的矩阵视角

真实计算里，一句话的所有词是打包成矩阵一次算完的。

```text
        输入序列（4 个 token，每个 d 维）
        ┌────────────────┐
   X =  │ x1 x2 x3 x4    │   形状: 4 × d
        └────────────────┘
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
       Q      K      V        各自形状: 4 × d

       Q × Kᵀ  ──▶  注意力分数矩阵 (4 × 4)

              到 x1  到 x2  到 x3  到 x4
       从 x1 [ 0.7   0.1   0.1   0.1 ]
       从 x2 [ 0.2   0.6   0.1   0.1 ]
       从 x3 [ 0.1   0.3   0.5   0.1 ]
       从 x4 [ 0.1   0.1   0.2   0.6 ]
              （每行经 softmax 后加起来为 1）
              │
              ▼
       分数矩阵 × V  ──▶  输出 (4 × d)
```

> **说明 · 这里藏着"上下文越长越贵"的原因**
>
> 注意力分数矩阵是 **n × n** 的（n = token 数）。序列长度翻一倍，这个矩阵的面积变成 **4 倍**。这就是长上下文昂贵的根本原因，也是各家厂商拼命研究稀疏注意力、滑动窗口的动机。第 05 章讲上下文工程时会再回到这里。

## 三、多头注意力：一个视角不够用

一次注意力只能表达一种"关注模式"。但语言里同时存在多种关系：语法主谓、指代、修饰、情感倾向……

多头（multi-head）的做法很直接：**并行做 h 次注意力，每次用不同的 W_Q / W_K / W_V，最后把结果拼起来再融合一次**。

```text
                      ┌── 头1（可能学到：主谓关系）──┐
                      ├── 头2（可能学到：指代消解）──┤
输入 ─────────────────┼── 头3（可能学到：邻近词） ──┼──▶ 拼接 ──▶ 线性层 ──▶ 输出
                      ├── 头4（可能学到：句法距离）─┤
                      └── ...（通常 8～128 个头） ───┘
```

几个要点：

- 每个头的维度会**缩小**（比如 d=1024，8 个头则每头 128 维），所以总计算量和单头相近。
- 各头学到什么**没人指定**，是训练涌现的。事后研究发现确实有头专门负责指代、有头专门看相邻词。
- 拼接后要过一个线性层，让各头的信息混合。

> 类比：让 8 个不同专业的人同时读同一句话——语法学家、语义学家、逻辑学家……然后开会汇总。比只让一个人读要全面。

## 四、位置编码：注意力天生"不认顺序"

这是很多人忽略的关键点。**自注意力本身完全不知道词序**。

```text
"狗 咬 人"   和   "人 咬 狗"
```

在纯注意力眼里，这两句是一模一样的一堆向量集合——因为加权求和满足交换律，打乱顺序结果不变。这显然不可接受。

解决办法：**在输入向量里显式注入位置信息**。

```text
最终输入 = 词嵌入(内容) + 位置编码(位置)

  "狗" 在位置 0 → 词向量[狗] + 位置向量[0]
  "咬" 在位置 1 → 词向量[咬] + 位置向量[1]
  "人" 在位置 2 → 词向量[人] + 位置向量[2]
```

主流做法有几类：

| 方案 | 思路 | 特点 |
| --- | --- | --- |
| 正弦位置编码 | 用不同频率的三角函数生成固定向量 | 原始论文方案，无需训练 |
| 可学习位置嵌入 | 每个位置一个可训练向量 | 简单，但无法外推超过训练长度 |
| 相对位置编码 | 只编码"相距多远" | 更适合长序列 |
| RoPE（旋转位置编码） | 通过旋转向量注入相对位置 | 当前主流，长度外推性好 |

> **说明 · 上下文窗口为什么是"硬"上限**
>
> 一部分原因就在位置编码：模型训练时只见过某个长度范围内的位置信号，超出后位置表示会失真，输出质量断崖式下跌。现在的长上下文模型靠 RoPE 变体 + 长文本继续训练来推高这个上限，但它始终是**有代价、有边界**的，不是无限的。

## 五、Encoder-Decoder 与 Decoder-only

原始 Transformer 有两半，但今天的 LLM 基本只用了其中一半。搞清楚这件事，你才能理解 LLM 的行为特点。

### 5.1 三种注意力布局

```text
【Encoder：双向注意力】适合"理解"
   每个词都能看到左边和右边
   我 ↔ 爱 ↔ 编 ↔ 程
   代表：BERT。用于分类、检索、打分

【Decoder：因果注意力（带掩码）】适合"生成"
   每个词只能看到自己和左边
   我 → 爱 → 编 → 程
   位置 3 看不到位置 4，因为生成时它还不存在
   代表：GPT 系列

【Encoder-Decoder】适合"转换"
   编码器双向读源文，解码器单向生成译文，中间用交叉注意力连接
   代表：原始 Transformer、T5，典型任务是翻译
```

### 5.2 因果掩码长什么样

因果掩码就是在注意力分数矩阵上盖一个上三角的"禁止区"：

```text
        看 t1  看 t2  看 t3  看 t4
  t1  [  ✓     ✗     ✗     ✗  ]
  t2  [  ✓     ✓     ✗     ✗  ]
  t3  [  ✓     ✓     ✓     ✗  ]
  t4  [  ✓     ✓     ✓     ✓  ]

  ✗ 位置的分数被设成负无穷，softmax 后权重为 0
```

### 5.3 为什么 LLM 选择 Decoder-only

这不是随便挑的，有四条硬理由：

1. **训练目标统一且通用**。"预测下一个 token"这一个目标就能覆盖翻译、摘要、问答、写代码——只要把任务写进上下文里。Encoder-Decoder 需要成对的输入输出数据，而纯文本到处都是。
2. **训练信号更密集**。一段 1000 token 的文本，Decoder-only 能产生 1000 个预测任务（每个位置都预测下一个）。这让数据利用率极高。
3. **架构简单，好扩规模**。只有一叠相同的层，扩到千亿参数时工程上更好切分。
4. **天然适配对话**。多轮对话本质就是一个不断变长的序列，把历史拼在前面继续生成即可，不需要区分"输入"和"输出"。

> **提示 · 这解释了智能体的一个核心事实**
>
> 在 Decoder-only 模型眼里，**没有"系统提示词/用户消息/工具结果"的本质区别**，它们最终都被拼成一个长序列。所谓角色（role）只是训练时约定的特殊标记。所以"上下文工程"的本质就是——**你在精心编排这个长序列的内容和顺序**。第 05、06 章会展开。

## 六、token 在里面走了一遍什么路

把整条链路串起来，看一个字符串从进入模型到吐出结果发生了什么。

```text
1. 分词（Tokenize）
   "你好，world" ──▶ [15496, 3574, 11, 6894]
                     （每个数字是词表里的编号）

2. 嵌入（Embedding）
   编号 ──▶ 查表 ──▶ 向量 (每个 token 变成 d 维向量)
   加上位置编码

3. N 层 Transformer Block（N 常见 32～100+）
   ┌────────────────────────────┐
   │  多头自注意力               │
   │      ↓                     │
   │  残差连接 + 层归一化        │
   │      ↓                     │
   │  前馈网络（FFN）            │
   │      ↓                     │
   │  残差连接 + 层归一化        │
   └────────────────────────────┘
        重复 N 次

4. 输出层
   最后一个位置的向量 ──▶ 映射到词表大小的分数
   ──▶ softmax ──▶ 概率分布
   ──▶ 按 temperature / top-p 采样 ──▶ 下一个 token

5. 把新 token 拼到序列末尾，回到第 3 步
```

关于这张图的两点补充：

- **残差连接**（把输入直接加到输出上）是深层网络能训起来的关键，它给梯度提供了一条"高速公路"。
- **前馈网络**占了参数量的大头。有研究认为它承担了"知识存储"的角色，注意力负责"信息路由"。

## 七、为什么能并行，又为什么慢

这是初学者最容易混淆的地方：Transformer 到底快不快？答案是**训练快，推理慢**，原因不同。

### 7.1 训练：完全并行

训练时整句话都是已知的，因果掩码保证了不会作弊，所以所有位置可以**一次性同时**计算。

```text
RNN 训练：  t1 → t2 → t3 → ... → t1000   （1000 个串行步）
Transformer：[ t1 t2 t3 ... t1000 ]      （1 步矩阵运算搞定）
```

这就是 Transformer 能把模型做到千亿参数的直接原因——**GPU 终于能被喂饱了**。

### 7.2 推理：必须自回归

生成时，第 n+1 个 token 依赖第 n 个 token 的结果，无法跳过。

```text
输入 "写一个"
  ▶ 生成 "函" ──▶ 输入变成 "写一个函"
  ▶ 生成 "数" ──▶ 输入变成 "写一个函数"
  ▶ 生成 "来" ──▶ ...
  每生成一个 token = 一次完整的前向传播
```

这直接解释了三件你在 Pi 里天天看到的事：

- **为什么输出是流式的**：token 本来就是一个个产生的，与其等全部生成完，不如边生边发。
- **为什么输出 token 比输入 token 贵**：输入可以并行处理一次，输出必须逐个前向传播。
- **为什么有 KV 缓存**：前面 token 的 Key/Value 算过一次就不变了，缓存下来能省掉大量重复计算。这也是"提示缓存"（第 12 章）能省钱的底层原理。

### 7.3 一张对比表收尾

| 维度 | RNN / LSTM | Transformer |
| --- | --- | --- |
| 训练并行度 | 无法并行 | 完全并行 |
| 长距离依赖 | 随距离衰减 | 任意两点直接连通 |
| 单层计算复杂度 | 与长度线性相关 | 与长度平方相关 |
| 推理方式 | 自回归 | 自回归（同样逐 token） |
| 可扩展到千亿参数 | 实践上不可行 | 可行 |

> 记住这个权衡：Transformer 用**平方级的计算代价**，换来了**任意距离的直接连接**和**完全的训练并行**。上下文窗口的一切限制与成本，都源于这笔交易。

## 八、这些原理在 Pi 里的落点

你不会在 Pi 的源码里看到矩阵乘法——它是模型的使用者，不是实现者。但上面的原理决定了它必须处理的现实：

- 模型输出是**逐块流式**的，所以 `packages/ai` 定义了一整套流式事件类型（`text_delta`、`thinking_delta` 等），第 21 章细讲。
- 上下文有硬上限，所以模型元数据里有 `contextWindow` 和 `maxTokens` 两个字段（`packages/ai/src/types.ts` 的 `Model` 接口），第 05 章解释它们的区别。
- 历史会无限增长而窗口不会，所以运行时必须有**上下文压缩**机制，第 30 章拆解。
- KV 缓存的存在，让"把稳定内容放在提示词前面"变成一条真实能省钱的工程规则，第 12、24 章讲缓存控制。
