# 第 04 章 · 推理模型与思维链（CoT / thinking）

> 2022 年，有人发现只要在提示词末尾加一句"让我们一步一步思考"，模型的数学题正确率就能从 18% 跳到 79%。这个几乎荒诞的发现，最终演化成了今天的推理模型（reasoning model）。这一章讲清楚：为什么"先想再答"有用、模型的"思考"到底是什么、以及它如何被 Pi 建模成一种内容块。

## 学习目标

- 理解思维链（Chain-of-Thought, CoT）是什么，以及它为什么有效
- 说清"提示词技巧"的 CoT 与"训练出来"的推理模型的区别
- 看懂 Pi 如何用 `ThinkingContent` 类型承载思考内容
- 知道 thinking budget / effort 是在控制什么、代价是什么
- 理解推理模型与智能体循环的关系，以及什么时候该开、什么时候不该开

## 一、从一个具体例子开始

先感受一下差别。

### 1.1 不思考的回答

```text
问：一家店卖苹果，第一天卖出库存的一半又 3 个，第二天卖出剩下的一半
    又 2 个，最后剩 4 个。原来有多少个？

直接作答：15 个。      ← 错
```

模型在这里做的事，本质上是"看到这类题，凭模式直接吐一个看起来合理的数"。它没有中间过程可依附。

### 1.2 带思维链的回答

```text
问：（同上）请一步一步推理。

答：设最后剩 4 个，倒推。
    第二天卖出「剩下的一半又 2 个」，卖完剩 4：
      设第二天开始时有 x，则 x - (x/2 + 2) = 4
      x/2 - 2 = 4 → x = 12
    第一天卖出「库存的一半又 3 个」，卖完剩 12：
      设原有 y，则 y - (y/2 + 3) = 12
      y/2 - 3 = 12 → y = 30
    验证：30 → 卖 18 剩 12 → 卖 8 剩 4 ✓
    答案：30 个。      ← 对
```

同一个模型，同样的参数，唯一的区别是**它把中间步骤写出来了**。

## 二、为什么"写出来"就变准了

这不是心理暗示，有清晰的机制解释。回想第 02 章：模型是自回归的，每生成一个 token 就做一次前向传播。

```text
不写过程：
  [问题] ──▶ 一次前向 ──▶ 直接产出答案
             ↑
        全部推理必须在这一次前向的
        有限层数里"一闪而过"地完成

写出过程：
  [问题] ──▶ "设" ──▶ "最后" ──▶ "剩" ──▶ "4" ──▶ ... ──▶ "30"
             每个 token 都是一次完整前向
             且后面的步骤能读到前面已写出的结论
```

三条具体原因：

1. **计算量随长度增加**。模型的层数是固定的，单次前向的"思考深度"有上限。多生成 200 个 token，就是多做了 200 次前向传播，总计算量提升了两个数量级。
2. **中间结果被外化成上下文**。写出"x = 12"之后，这个结论就变成了序列里的实实在在的 token，后续步骤可以通过注意力直接读取它，不需要"记在心里"。**上下文成了模型的草稿纸和工作记忆**。
3. **降低了每一步的难度**。把"一步跳到答案"拆成十个小步，每一步都是模型在训练数据里见过千百遍的简单模式（解一元一次方程、做减法）。

> **提示 · 一句话记住它**
>
> **思维链把"一次性的深度推理"换成了"多次浅层推理的串联"。** 这也解释了它的边界：如果某一步本身就超出模型能力（比如大数乘法），拆步骤也救不了它——那时候你需要的是工具（第 07 章），不是思维链。

## 三、CoT 的三种形态

### 3.1 Few-shot CoT：给例子

在提示词里放几个带完整推理过程的示范。

```text
问：食堂有 23 个苹果，用掉 20 个，又买了 6 个，现在有几个？
答：一开始 23 个，用掉 20 个后剩 23-20=3 个，又买 6 个，
    3+6=9。答案是 9。

问：小明有 5 个球，又买了 2 筒，每筒 3 个，一共几个？
答：
```

模型会模仿示范的格式，自然而然地展开推理。

### 3.2 Zero-shot CoT：一句咒语

不给例子，只加一句触发语。

```text
"Let's think step by step."
"让我们一步一步分析。"
"请先分析问题，再给出答案。"
```

它有效是因为预训练数据里，这类句子后面**统计上**跟着的就是详细推理过程。你不是在"命令"模型思考，而是在把它引导到语料中"认真解题"的那个分布上去。

### 3.3 训练出来的推理模型

前两种是**使用技巧**，第三种是**模型本身的能力**。

以 DeepSeek-R1、OpenAI o 系列为代表的推理模型，通过大规模强化学习专门训练"长链条思考"。它们的特点是：

- **不需要你提示**，遇到难题会自动展开长推理。
- 推理链可以长达**数千甚至上万 token**，包含分支尝试、自我怀疑、回溯纠错。
- 训练时的奖励信号往往来自**可自动验证的结果**（数学题答案对不对、代码能不能跑通），所以在这些领域提升尤其显著。

一段典型的推理模型内部思考长这样：

```text
用户问的是斐波那契数列第 50 项。
先想清楚要不要用递归——不行，指数复杂度会炸。
用迭代吧。a=0, b=1，循环 50 次...
等等，题目说"第 50 项"，是从 0 开始索引还是 1 开始？
歧义。我按常见约定 F(0)=0, F(1)=1 来算，并在答案里注明约定。
另外 F(50) = 12586269025，超过 32 位整数范围，
如果用户是写 C 语言要提醒用 long long。
好，现在组织答案。
```

注意其中的**自我质疑（"等等"）和回溯**——这是长链推理训练带来的最有价值的行为。

## 四、Pi 如何建模「思考」

这段思考内容不能和正式回答混在一起：它是给模型自己看的草稿，不是给用户看的结论。所以协议层必须把它区分开。

在 `packages/ai/src/types.ts` 里，思考被定义成一种独立的内容块：

```ts
export interface ThinkingContent {
	type: "thinking";
	thinking: string;
	thinkingSignature?: string; // 例如 OpenAI Responses 的 reasoning item ID
	/** 被安全过滤器屏蔽时为 true，加密载荷存在 thinkingSignature 里，
	 *  以便多轮对话继续时能原样传回 API */
	redacted?: boolean;
}
```

它和文本、工具调用并列，共同组成助手消息的内容数组：

```ts
export interface AssistantMessage {
	role: "assistant";
	content: (TextContent | ThinkingContent | ToolCall)[];
	// ...
}
```

这个设计有三个值得学习的地方：

### 4.1 思考是「内容块」，不是「字段」

一条助手消息的 content 是个**数组**，可以是：

```text
[ ThinkingContent, TextContent ]                  ← 想了想，然后回答
[ ThinkingContent, ToolCall ]                     ← 想了想，然后调工具
[ ThinkingContent, TextContent, ToolCall, ToolCall ] ← 想、说、并行调两个工具
[ TextContent ]                                   ← 简单问题，不思考
```

用数组而不是 `thinking: string` 字段，意味着**顺序信息被保留**了，UI 可以按真实发生顺序渲染，重放时也能还原完整过程。

### 4.2 签名（signature）是为了多轮延续

`thinkingSignature` 是个容易被忽略但很关键的字段。部分厂商出于安全考虑，不会把完整思考内容原文返回给你，而是给一个**加密句柄**。下一轮请求时你必须把这个句柄原样传回去，模型才能接上上一轮的思路。

`redacted: true` 就是这种情况：思考内容被屏蔽了，但加密载荷还在 `thinkingSignature` 里。Pi 必须原样保管并回传——**不能因为"看不懂就丢掉"**。

> **注意 · 这是自己写 Agent 时的经典坑**
>
> 很多人实现多轮对话时，会把助手消息"简化"成只保留纯文本再发回去。对推理模型这样做，轻则思路断裂、质量下降，重则被 API 直接报错拒绝。**助手消息必须尽可能原样回传**，包括你看不懂的签名字段。

### 4.3 流式事件里思考是独立通道

思考内容是流式产生的，Pi 为它定义了专门的事件：

```ts
| { type: "thinking_start"; contentIndex: number; partial: AssistantMessage }
| { type: "thinking_delta"; contentIndex: number; delta: string; partial: AssistantMessage }
| { type: "thinking_end"; contentIndex: number; content: string; partial: AssistantMessage }
```

和文本的 `text_start` / `text_delta` / `text_end` 完全平行。这样 UI 就能做到"思考过程折叠显示、正式回答正常显示"。第 21 章会完整拆解事件流。

## 五、thinking budget 与 effort：给思考装一个旋钮

思考不是免费的。思考 token 按**输出 token 计费**，而输出 token 通常是最贵的。一道简单问题让模型想 5000 token，就是纯粹的浪费。

所以需要一个控制维度。Pi 把它抽象成统一的**思考等级**：

```ts
export type ThinkingLevel = "minimal" | "low" | "medium" | "high" | "xhigh" | "max";
export type ModelThinkingLevel = "off" | ThinkingLevel;
```

以及针对"按 token 预算"的厂商的具体预算映射：

```ts
/** Token budgets for each thinking level (token-based providers only) */
export interface ThinkingBudgets {
	minimal?: number;
	low?: number;
	medium?: number;
	high?: number;
}
```

### 5.1 为什么需要这层抽象

因为各家厂商的接口形态完全不一样。同样是"多想一会儿"这个诉求：

| 厂商风格 | 参数形态 |
| --- | --- |
| OpenAI 风格 | `reasoning_effort: "low" / "medium" / "high"` |
| 预算型 | 直接给一个 token 数上限 |
| 开关型 | `thinking: { type: "enabled" }` |
| 布尔型 | `enable_thinking: true` |
| 模板型 | 通过 chat template 参数注入 |

Pi 在 `packages/ai/src/types.ts` 里用 `thinkingFormat` 字段枚举了这些差异，并用 `thinkingLevelMap` 把统一的等级映射到具体厂商的取值。上层代码只说 `reasoning: "high"`，适配层负责翻译。**这就是"抽象层"存在的意义**——第 17、18 章会看到具体实现。

### 5.2 该开多大

一个实用的经验表：

| 任务类型 | 建议等级 | 理由 |
| --- | --- | --- |
| 改一个变量名、格式化 | off / minimal | 思考纯属浪费 |
| 常规代码编写 | low / medium | 需要一点规划 |
| 调试复杂 bug | high | 需要假设—验证的多轮推演 |
| 架构设计、算法优化 | high / max | 需要比较多个方案 |
| 大批量机械操作 | off | 成本和延迟优先 |

> **说明 · 思考等级不是越高越好**
>
> 除了成本，还有两个真实代价：
> 1. **首字延迟**。开高思考等级时，用户可能要等十几秒才看到第一个字，因为模型在闷头想。
> 2. **过度思考**。简单问题给高预算，模型会把自己绕进去——反复推翻正确的初始判断，最后给出更差的答案。这个现象在实测中相当常见。

### 5.3 成本要看清楚

在 Pi 的用量统计里，思考 token 是这样记的：

```ts
/**
 * Reasoning/thinking tokens, when the provider reports them. This is a subset of
 * `output`: `output` already includes these tokens.
 */
reasoning?: number;
```

**关键点：`reasoning` 是 `output` 的子集，不是额外的一项。** 算成本时别重复计算，但要意识到——你付的输出费里，可能一大半买的是用户根本看不到的思考过程。

## 六、思考与智能体循环的关系

这是本章最重要的一节。推理模型不只是"回答得更好"，它改变了智能体循环的质量。

### 6.1 在循环的哪个位置

```text
┌──────────────────────────────────────────────────────┐
│  上下文 = 系统提示词 + 历史消息 + 工具结果            │
│              │                                       │
│              ▼                                       │
│     ┌─────────────────┐                              │
│     │  思考阶段        │  ← thinking 内容块产生于此    │
│     │  · 现在处于什么状态                             │
│     │  · 上一个工具结果说明了什么                     │
│     │  · 下一步该做什么、用哪个工具                   │
│     └────────┬────────┘                              │
│              ▼                                       │
│     ┌─────────────────┐                              │
│     │  决策输出        │                              │
│     │  文本回答 或 工具调用                           │
│     └────────┬────────┘                              │
│              ▼                                       │
│        执行工具 → 结果回填上下文 → 回到顶部            │
└──────────────────────────────────────────────────────┘
```

**每一轮循环，模型都有一次思考机会。** 这意味着思考不是一次性的，而是贯穿整个任务过程的持续判断。

### 6.2 思考在多轮任务里承担什么

一个真实的编码任务，思考内容通常在做四件事：

```text
轮次 1 思考：用户要我修复登录 bug。我还不知道代码结构，
            先搜索 login 相关文件。
   → 调用 grep 工具

轮次 2 思考：搜到 3 个文件，auth.ts 看起来是核心。
            但我还不知道 bug 具体表现，先读这个文件。
   → 调用 read 工具

轮次 3 思考：看到了。第 42 行 token 过期判断用了 <= 而不是 <，
            边界情况会误判。等等——我得先确认时间单位，
            上面 expiresAt 是秒还是毫秒？再看一眼常量定义。
   → 调用 read 工具（另一个文件）

轮次 4 思考：确认了是毫秒。修改方案成立。改这一处即可，
            改完应该跑一下相关测试。
   → 调用 edit 工具
```

四件事分别是：**状态评估、信息缺口识别、假设验证、行动规划**。没有思考通道，这些判断也会发生，但会混在正式输出里，既污染给用户看的内容，也更容易被跳过。

### 6.3 一个必须注意的工程细节

思考内容会不会保留在后续轮次的上下文里？各家策略不同，而且**这会显著影响行为和成本**：

```text
策略 A · 全部保留
  优点：模型能看到自己之前的推理，连贯性好
  缺点：上下文膨胀极快，长任务很快撑爆窗口

策略 B · 只保留最近一轮
  优点：成本可控
  缺点：可能重复之前已经排除过的思路

策略 C · 保留签名不保留原文
  厂商强制的做法，靠加密句柄维持连续性
```

Pi 通过 `transformMessages`（第 20 章）来处理这类差异——**同一份消息历史，发给不同厂商时会被转换成不同形态**。`redacted` 和 `thinkingSignature` 就是为策略 C 服务的。

## 七、什么时候不要用推理模型

反过来说同样重要。以下场景开思考是负收益：

- **强调低延迟的交互**。补全、实时建议，用户等不了十几秒。
- **大批量机械任务**。给 500 个文件加版权头，思考纯属烧钱。
- **答案唯一且简单的查询**。"这个函数在哪个文件"，搜索工具直接给答案。
- **已经有明确指令的执行**。用户说得清清楚楚"把第 42 行的 `<=` 改成 `<`"，不需要模型再想。

> 好的智能体应该**按任务动态调节思考等级**，而不是全局开满。这也是为什么 Pi 把 `ThinkingLevel` 做成可按请求传入的选项（`StreamOptions` 中的 `reasoning` 字段），而不是写死在配置里。

## 八、给自己写 Agent 的四条落地建议

1. **把 thinking 建模成独立内容块**，不要和正式文本混在一个字符串里。参考 `ThinkingContent` 的三字段设计：内容、签名、是否被屏蔽。
2. **助手消息原样回传**，包括签名字段。看不懂的字段更要保留。
3. **暴露思考等级给上层**，并提供合理默认值。做成一个统一枚举，各厂商差异在适配层消化。
4. **UI 上默认折叠思考内容**。用户想看时能展开，但默认不该被几千字草稿淹没。同时把思考 token 数显示出来，让成本可见。
