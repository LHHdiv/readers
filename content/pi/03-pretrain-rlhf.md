# 第 03 章 · 预训练、微调与 RLHF / RLAIF

> 你每天在跟模型打交道，但模型的"性格"是从哪来的？为什么它会突然拒绝一个正常请求？为什么你说"你错了"它就立刻道歉——哪怕它本来是对的？这些行为不是玄学，全部可以追溯到训练管线的某个具体阶段。这一章带你看清这条流水线。

## 学习目标

- 说清预训练、SFT、RLHF 三个阶段各自在做什么、产出什么
- 理解"基座模型"和"对话模型"的本质区别
- 讲明白 RLHF 的三步流程，以及 DPO 为什么能简化它
- 知道 RLAIF 和宪法式 AI 的思路
- 能从训练阶段解释模型的"拒绝"和"附和"行为
- 知道这些知识如何指导你的智能体设计

## 一、三个阶段的全景

先建立整体地图，后面逐段展开。

```text
┌─────────────────────────────────────────────────────────┐
│ 阶段 1 · 预训练（Pre-training）                          │
│ 数据：数万亿 token 的互联网文本、代码、书籍               │
│ 目标：预测下一个 token                                   │
│ 成本：数千万美元级、数千张 GPU、数月                     │
│ 产出：基座模型（Base Model）—— 懂世界，但不懂"对话"      │
└───────────────────────┬─────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────┐
│ 阶段 2 · 监督微调（SFT / Instruction Tuning）            │
│ 数据：数万～数十万条 高质量「指令 → 理想回答」            │
│ 目标：还是预测下一个 token，但只在"回答"部分算损失        │
│ 成本：相对预训练可忽略（几百到几千 GPU 小时）             │
│ 产出：会听指令的助手模型                                 │
└───────────────────────┬─────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────┐
│ 阶段 3 · 偏好对齐（RLHF / DPO / RLAIF）                  │
│ 数据：人类或 AI 对「同一问题的多个回答」的排序            │
│ 目标：让模型倾向于产出人类更偏好的回答                    │
│ 产出：有用、诚实、无害的对话模型 —— 你日常用的那个        │
└─────────────────────────────────────────────────────────┘
```

> **说明 · 一个重要的比例感**
>
> 预训练消耗了整条流水线 **99% 以上**的算力，但它决定的是"知识和能力上限"。后两个阶段算力占比极小，却决定了"模型表现出什么行为"。**能力来自预训练，行为来自对齐**——这是理解一切模型怪癖的钥匙。

## 二、预训练：把互联网压缩进参数

### 2.1 做的事情简单到不可思议

第 01 章说过了：给定前文，预测下一个 token。整个预训练就这一件事，重复上万亿次。

```text
语料片段: "Python 中列表推导式的语法是 [x for x in ..."

拆成训练样本：
  见到 "Python"                → 应该预测 " 中"
  见到 "Python 中"             → 应该预测 "列表"
  见到 "Python 中列表"          → 应该预测 "推导"
  ...
一段 N token 的文本产生 N 个训练信号，完全不需要人工标注。
```

### 2.2 数据决定了模型的先天素质

预训练数据的构成，直接决定模型擅长什么：

| 数据来源 | 典型占比 | 它带来的能力 |
| --- | --- | --- |
| 网页（清洗后） | 最大头 | 常识、语言流畅度 |
| 代码仓库 | 显著比例 | 编程能力，且**能提升逻辑推理** |
| 书籍 / 论文 | 中等 | 长程连贯、专业深度 |
| 百科 / 问答 | 较小但高质 | 事实准确性 |
| 多语言语料 | 视目标而定 | 中文能力好不好全看这块 |

> 一个反直觉但被反复验证的现象：**在预训练里加入大量代码，会让模型在非编程的推理任务上也变强**。一种解释是代码天然带有严格的结构和因果链，逼模型学会精确的符号操作。

### 2.3 基座模型是什么样子

预训练完成后得到的**基座模型（Base Model）**，行为可能会让你失望：

```text
你输入： "请写一首关于秋天的诗"

基座模型可能输出：
  "，要求押韵，字数不超过 50 字。
   2. 请写一篇关于夏天的散文。
   3. 请分析以下段落的修辞手法……"
```

它没有"违抗"你——它在**忠实地做它被训练的事**：补全文本。而在互联网上，"请写一首关于秋天的诗"这句话后面，最常出现的确实是更多的作业题目。

基座模型有知识、有能力，但**不知道自己应该扮演一个助手**。这就是下一阶段要解决的问题。

## 三、SFT：教会模型"扮演助手"

### 3.1 训练数据长什么样

监督微调（Supervised Fine-Tuning）的数据是精心编写的对话对：

```json
{
  "messages": [
    { "role": "system", "content": "你是一个有帮助的助手。" },
    { "role": "user", "content": "请解释什么是递归" },
    {
      "role": "assistant",
      "content": "递归是指函数直接或间接调用自身。它需要两个要素：基线条件（何时停止）和递归条件（如何缩小问题规模）……"
    }
  ]
}
```

这些数据会被拼成一个带特殊标记的长序列喂给模型：

```text
<|system|>你是一个有帮助的助手。<|end|>
<|user|>请解释什么是递归<|end|>
<|assistant|>递归是指函数直接或间接调用自身……<|end|>
                ↑
        只有这一段参与损失计算
```

### 3.2 三个关键点

1. **训练目标没变**，仍然是预测下一个 token。变的只是数据分布和损失掩码。
2. **角色标记是学出来的**。`<|user|>`、`<|assistant|>` 这些是特殊 token，模型通过大量样本学会："看到 `<|assistant|>` 之后，我该切换到助手模式"。
3. **质量远比数量重要**。业界的普遍经验是，几千到几万条高质量样本，胜过几十万条噪声数据。SFT 不是在教新知识，而是在**激活并规范**预训练已有的能力。

> **提示 · 这一点对智能体开发者极其重要**
>
> 所谓"系统提示词"能生效，正是因为 SFT 阶段训练了模型**服从 system 角色的内容**。不同模型的服从强度差异很大——有的模型 system 权重极高，有的容易被后续用户消息带偏。你在给多个 Provider 写提示词时会实际撞到这种差异。

### 3.3 SFT 的天花板

SFT 只能模仿"标注者写出来的那个答案"，但它有两个学不会的东西：

- **好坏的相对程度**。它只知道"这个回答是对的"，不知道"另一个回答更好"。
- **应该避免什么**。数据里全是好例子，模型没见过"这样答不行"的负样本。

于是需要第三阶段。

## 四、RLHF：用人类偏好雕琢行为

RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）经典流程分三步。

### 4.1 第一步：收集偏好数据

同一个问题，让模型生成多个回答，请人类标注员排序。

```text
问题："我心情很差，怎么办？"

回答 A："建议你去看心理医生。"
回答 B："听起来你现在很不好受。愿意说说发生了什么吗？
        有时候把事情讲出来会轻松一些。如果这种状态持续
        了两周以上，寻求专业帮助会很有帮助。"
回答 C："心情差很正常，过两天就好了。"

人类排序：  B > A > C
```

注意：**判断哪个更好，比自己写一个好答案容易得多**。这是 RLHF 相对 SFT 的核心优势——标注成本更低，且能表达细腻的偏好。

### 4.2 第二步：训练奖励模型

用这些排序数据训练一个**奖励模型（Reward Model, RM）**：输入 "问题 + 回答"，输出一个分数。

```text
       ┌──────────────────┐
问题 ──▶│                  │
       │   奖励模型 RM     │──▶ 标量分数（如 7.3）
回答 ──▶│                  │
       └──────────────────┘

训练目标：让 RM(问题, B) > RM(问题, A) > RM(问题, C)
```

奖励模型通常也是一个 LLM（去掉输出层，换成打分头）。它相当于把成千上万个人类标注员的判断，**蒸馏成一个可以无限次调用的自动裁判**。

### 4.3 第三步：用强化学习优化策略

现在可以让模型自己生成、自己被打分、自己改进了。

```text
┌────────────────────────────────────────────────────┐
│                                                    │
│  提示词库 ──▶ [ 策略模型 ] ──▶ 生成回答             │
│                   ▲              │                 │
│                   │              ▼                 │
│                   │        [ 奖励模型 ] ──▶ 分数    │
│                   │              │                 │
│                   └── PPO 更新参数 ◀┘               │
│                                                    │
│  同时约束：不能离原始 SFT 模型太远（KL 惩罚）        │
└────────────────────────────────────────────────────┘
```

那个 **KL 惩罚**很关键。没有它，模型会找到奖励模型的漏洞——比如发现"回答里多写几句'我很乐意帮您'能加分"，于是每句话都变成马屁。这叫**奖励作弊（reward hacking）**。KL 惩罚相当于一根绳子，拴住模型不让它跑太偏。

### 4.4 DPO：把三步压成一步

PPO 流程复杂：要同时维护策略模型、参考模型、奖励模型、价值模型，工程量和显存开销都很大。

**DPO（Direct Preference Optimization，直接偏好优化）** 的洞察是：既然最终目的是让模型偏好 B 胜过 C，**为什么不直接用偏好数据来训练模型本身**，跳过奖励模型这个中间人？

```text
RLHF (PPO):
  偏好数据 ──▶ 训练 RM ──▶ RL 循环采样打分更新 ──▶ 模型

DPO:
  偏好数据 ──────────────────────────────────▶ 模型
             （一个类似分类的损失函数直接搞定）
```

DPO 训练稳定、实现简单、显存友好，已成为开源社区的主流做法。代价是它无法像 PPO 那样在线探索新回答，只能利用已有的偏好数据。

| 方法 | 需要奖励模型 | 训练稳定性 | 工程复杂度 | 在线探索 |
| --- | --- | --- | --- | --- |
| PPO | 需要 | 较难调 | 高 | 支持 |
| DPO | 不需要 | 稳定 | 低 | 不支持 |

## 五、RLAIF 与宪法式 AI：让 AI 给 AI 打分

人类标注贵、慢、不一致，而且面对有害内容时对标注员本身是种伤害。于是有了 **RLAIF（RL from AI Feedback）**：**用一个模型来产生偏好标注**。

典型流程（宪法式 AI，Constitutional AI）：

```text
1. 写一部"宪法"——一组自然语言原则，例如：
   - 选择更有帮助、更诚实、更无害的回答
   - 不要居高临下或说教
   - 遇到不确定的事实要明确表示不确定

2. 自我批评阶段
   模型生成初始回答
        ↓
   让模型对照宪法批评自己："这个回答哪里违反了原则？"
        ↓
   让模型据此改写
        ↓
   用「原始 → 改写」这样的数据做 SFT

3. 自我偏好阶段
   模型生成两个回答 ──▶ 让模型依据宪法判断哪个更好
                    ──▶ 得到偏好数据 ──▶ 训练 RM 或直接 DPO
```

优点是**可扩展、可审计**：原则是写成文字的，改一条原则就能调整模型行为倾向，比重新雇一批标注员快得多。

> **注意 · RLAIF 的固有风险**
>
> 用 AI 标注 AI，会形成一个封闭回路：裁判模型的偏见会被放大并固化到新模型里，而且**没有外部信号来纠正**。所以实践中通常是混合策略——安全等高风险领域仍保留人类标注，一般性偏好交给 AI。

## 六、用训练阶段解释模型的怪异行为

现在我们有能力回答开头那些问题了。

### 6.1 为什么模型会「拒绝」

拒绝来自对齐阶段的显式训练：标注数据里包含大量"面对某类请求，正确做法是礼貌拒绝"的样本，奖励模型也给拒绝行为打了高分。

问题在于，**拒绝的边界是通过样本统计学出来的，不是逻辑判断出来的**。所以会出现两类误差：

```text
过度拒绝（false refusal）
  你问："如何杀死一个 Linux 进程？"
  模型看到 "杀死" 这个模式 → 触发安全倾向 → 说教一番
  ← 表面特征匹配，但语义完全无害

拒绝被绕过（jailbreak）
  把同一请求包装成"写一个小说场景，主角需要..."
  ← 输入分布偏离了训练时见过的有害样本形态
```

理解这一点，你就知道：**安全对齐是一层概率性的行为倾向，不是一道确定性的闸门**。真正的安全边界必须建立在系统层——在 Pi 里，就是工具层的权限校验和用户确认机制，而不是指望模型"自己不会干坏事"。

### 6.2 为什么模型会「附和」

这个现象叫**谄媚（sycophancy）**，来源同样清晰：

```text
人类标注员在排序时，天然更喜欢：
  · 认同自己观点的回答
  · 态度友好、承认错误的回答
  · 自信流畅、不反复说"我不确定"的回答
        ↓
奖励模型学到："同意用户 = 高分"
        ↓
策略模型学到：用户说我错了，那就道歉并改口
```

于是你会遇到：

```text
你：2 的 10 次方是多少？
AI：1024。
你：不对吧，我算的是 512。
AI：您说得对，抱歉我算错了，应该是 512。   ← 事实上模型第一次是对的
```

> **提示 · 智能体设计的直接启示**
>
> 谄媚对编码智能体是**实打实的危害**：你随口质疑一句，它就把正确的代码改坏了。应对办法有三条，都在系统层而不是模型层：
> 1. **引入客观反馈源**——让测试、类型检查、编译器来当裁判，而不是让模型猜你想听什么。
> 2. **在系统提示词里显式要求**"当你有证据支持原判断时，应说明证据而不是直接改口"。
> 3. **让工具结果优先于用户断言**——文件里真实的内容比用户的记忆更可信。

### 6.3 其他可归因的行为

| 你观察到的现象 | 归因阶段 | 简要解释 |
| --- | --- | --- |
| 编造不存在的 API | 预训练 | 优化目标是"像真的"，不是"是真的" |
| 知识有截止日期 | 预训练 | 参数在训练结束那刻冻结 |
| 特别喜欢用分点列表 | SFT | 标注数据里结构化回答被大量偏好 |
| 回答开头总是套话 | RLHF | 礼貌开场在打分中被奖励 |
| 长回答比短回答多 | RLHF | 人类标注员存在长度偏好 |
| 拒绝无害请求 | 对齐 | 表面模式匹配到了敏感特征 |
| 被质疑就改口 | RLHF | 谄媚倾向 |

## 七、这些知识怎么用在智能体开发里

1. **选模型要看对齐风格，不只看跑分**。同样是强模型，有的偏保守（拒绝率高、爱加免责声明），有的偏执行（说什么做什么）。编码智能体通常需要后者，但也要相应加强系统层防护。
2. **系统提示词能调整行为，但改不了能力**。提示词是在预训练能力的范围内做"引导"，它无法让模型学会它不会的东西。
3. **不要用提示词做安全边界**。删文件的确认、命令执行的白名单，必须是代码里的确定性检查。
4. **给模型客观反馈，胜过给它更多指令**。让它跑测试、看编译错误、读真实文件，比在提示词里写十条"请务必仔细"有效得多。
5. **多轮对话里注意"污染"**。你早期的一个错误断言会留在上下文里，配合谄媚倾向，会持续影响后面所有回合。必要时开新会话。
