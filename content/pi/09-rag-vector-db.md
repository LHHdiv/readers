# 第 09 章 · 检索增强 RAG 与向量数据库

## 9.1 先说痛点：LLM 的"知识截止"与"幻觉"

大模型有两个绕不开的先天缺陷：

- **知识截止（Knowledge Cutoff）**：模型只在训练数据上见过世界，训练之后发生的事（今天的股价、你刚写的代码）它一概不知。
- **幻觉（Hallucination）**：遇到不会的，它不会老实说"我不知道"，而是**一本正经编**——编得还挺像。

> 幻觉：模型生成与事实不符、但语言流畅自信的内容。就像考试时不会做也硬写，还写得理直气壮。

那怎么办？最朴素的想法：把资料**直接塞进 prompt**，让模型"现学现卖"。这招对短资料管用，但资料一长就崩（context window 装不下、塞太多模型反而注意力分散、还更贵）。RAG 是更系统的解法。

> **提示 · 本章和前面章节的关系**
>
> 第 7 章的工具调用，是 RAG 能"动起来"的关键——检索本身就是一个工具（`search_docs`）。RAG 让智能体拥有了"外接知识库"的能力，是智能体从"靠脑子"走向"靠资料"的转折点。

## 9.2 RAG 是什么：检索 → 增强 → 生成

**RAG = Retrieval-Augmented Generation（检索增强生成）**。名字就是流程：

```text
用户问题
   │
   ▼
① 检索 Retrieval：从知识库找出"和问题最相关的几段资料"
   │
   ▼
② 增强 Augmentation：把这几段资料拼进 prompt
   │
   ▼
③ 生成 Generation：模型带着资料回答问题（只准基于资料说）
```

核心转变：**答案的事实来源从"模型记忆"变成"检索到的资料"**。模型变成"基于给定文档作答的助手"，幻觉空间被压小。

> **说明 · 为什么叫"增强"而不是"替换"**
>
> RAG 不是让模型放弃记忆，而是**在记忆之外再喂一手资料**。模型依然负责理解、组织、表达；资料负责提供事实。两者配合，既准又顺。

## 9.3 Embedding：把文字变成"能比较相似度"的数字

检索的关键难题：怎么判断"哪段资料和问题相关"？不能靠关键词硬匹配（"怎么修登录"和"login 报错处理"字面不同但意思一样）。

解法：**Embedding（嵌入）**。用一个模型把一段文字变成一串固定长度的数字向量（如 1536 维）。语义相近的文字，向量在空间里也离得近。于是"相关性"就变成了"向量距离"——算余弦相似度即可。

```text
"北京天气怎么样"  ──embedding──▶ [0.12, -0.03, 0.88, ...]  向量 A
"查询北京气温"    ──embedding──▶ [0.11, -0.02, 0.86, ...]  向量 B
                                              ↑ A 与 B 距离很近 → 语义相似
```

直觉：**embedding 是把"意思"压缩成坐标**。意思越近，坐标越近。这是 RAG 能"懂语义"的根。

## 9.4 向量数据库：专门存"向量+原文"的仓库

算出来的向量和对应原文，得有个地方存、能快速"给我找最近的 N 个"。这就是**向量数据库**（如 Chroma、Qdrant、pgvector、Pinecone）。它干三件事：

1. 存：原文 + 它的 embedding 向量。
2. 查：给一个查询向量，返回最相似的 K 条（近似最近邻搜索，ANN）。
3. 管：增删改、分片、过滤。

```text
写入时：
  文档 ──切块──▶ 每块 ──embedding──▶ (向量, 原文) ──▶ 存入向量库

查询时：
  问题 ──embedding──▶ 查询向量 ──▶ 向量库 ANN 搜索 ──▶ 最相似的 K 块原文
```

## 9.5 Chunking：切块的艺术

embedding 是对"一段文字"算一个向量。一篇 100 页文档不能直接塞（太长、语义太杂）。要先**切块（Chunking）**：把文档切成小段，每块单独 embedding。

```text
长文档
   │
   ▼
切成若干 chunk（如每段 500 字，留 50 字重叠）
   │
   ▼
每块独立 embedding → 存入向量库
```

> **注意 · 切块大小是个真问题**
>
> 块太大：向量代表"杂糅语义"，检索不准。块太小：一句话脱离上下文，模型看不懂。重叠（overlap）能缓解"边界信息丢失"。没有万能参数，得按你的资料试。

RAG 质量的 80% 往往卡在"切块 + 检索召回"这两步，而非模型本身。

## 9.6 "喂文件" vs RAG：区别在哪

新手容易混。对比一下：

| 做法 | 怎么用资料 | 上限 | 成本 |
|------|------------|------|------|
| 直接把文件塞 prompt | 一次性全量塞进上下文 | 装不下长文件；塞多了模型走神 | 高（每次都付全量 token） |
| RAG | 先检索，只塞"相关几段" | 可扩展到海量知识库 | 低（只付相关段 token + 检索费） |

简言之：**"喂文件"是暴力全给，RAG 是精准按需给**。RAG 让知识库能大到塞不进任何一次 prompt。

## 9.7 Coding Agent 场景下的 RAG 变体

写代码的智能体（如 Pi）对"外部知识"的需求和聊天机器人不同。它的"知识"往往是**代码本身**，检索也变成代码检索：

- **代码块检索**：把仓库按文件/函数切块 embedding，问"谁调用了 login？"时先检索相关代码段再回答。
- **grep / 符号索引**：很多情况下不需要向量，直接 `grep` 函数名、读 AST（抽象语法树）索引更快更准。Pi 的工具集里就有文件读取、搜索类工具，本质上就是"代码世界的检索器"。
- **文档检索**：要理解某个第三方库用法，先抓官网文档块再喂给模型。

```text
用户：为什么 build 失败了？
   │
   ▼
Agent 检索：grep "build" 相关配置 + 读报错栈指向的文件
   │
   ▼
把相关片段拼进 prompt → 模型定位根因 → 调 edit 工具修复
```

> **说明 · 对"外接知识"的总结**
>
> RAG 的本质不是某个数据库，而是**一种架构思路：让模型在回答前，先去外部把事实捞上来**。在 coding agent 里，"外部"可能是向量库、grep 结果、或一次 web 搜索——形态各异，思路同源。这正好为后续"多工具、多知识源"的智能体打底。

## 9.8 RAG 的局限（别神话它）

- **检索不到 = 答不对**：如果相关资料没被召回，模型还是会瞎编。
- **拼进去的资料可能互相矛盾**，模型未必能分辨。
- **延迟与成本**：多一次检索往返。

所以工业级 RAG 常加"重排序（rerank）""引用溯源（标明答案出自哪段）""没检索到就直说不知道"等补丁。

## 9.9 重排序（Rerank）与混合检索

单纯向量检索有个软肋：语义近 ≠ 真相关。比如问"怎么退款"，可能召回一篇讲"怎么买"的文章（都聊交易，语义近但答非所问）。两个补强手段：

- **Rerank（重排序）**：先用向量粗召回 Top-K（如 20 条），再用一个更准的 rerank 模型把这 20 条"精排"出最相关 Top-N（如 3 条）喂给 LLM。两阶段，又快又准。
- **混合检索（Hybrid）**：向量检索管"语义"，关键词/BM25 检索管"字面精确匹配"（如专有名词、函数名）。两者结果融合，兼顾"懂意思"和"找得准"。

```text
查询 ──┬─▶ 向量检索 ──┐
      │              ├──▶ 融合/重排 ──▶ 最相关 Top-N ──▶ 拼进 prompt
      └─▶ 关键词检索 ─┘
```

## 9.10 怎么判断 RAG"好不好用"（评测）

RAG 不是接上就完事，要量化。常见看两个指标：

- **召回率（Recall）**：该召回的相关资料，有没有被检索到？召回不到，后面全白搭。
- **答案忠实度（Faithfulness）**：模型答案是不是真基于检索到的资料，还是自己编的？

工程上会造一批"问题—标准答案—相关文档"的测试集，自动跑：检索对不对、最终答得对不对。Pi 这类项目的文档/测试体系（如 `test.sh`、conformance 测试）也是同样思路——用可重复的例子验证行为。

## 9.11 元数据过滤与"谁能看什么"

真实知识库往往有权限：HR 文档不能给普通员工看。向量库通常支持给每段资料打**元数据标签**（如 `department: "hr"`、`level: "secret"`），检索时加过滤条件，只召回"当前用户有权看"的块。这一步在"拼进 prompt 之前"就挡掉越权内容，是 RAG 落地到企业场景的必做题。

> **说明 · 给 coding agent 的提醒**
>
> 代码仓库虽然一般不分权限，但"该检索哪部分"同样重要：改登录模块时，理应优先检索 `auth/` 目录而非 `docs/`。按路径/模块做元数据过滤或限定 grep 范围，能显著提升检索相关性和速度——本质还是 9.7 节说的"代码世界检索器"。

## 9.12 从 RAG 到 Agent 的"记忆"

RAG 是"外接知识"，还有一种常被混淆的概念叫**记忆（Memory）**：让 agent 跨多轮对话记住之前说过的话。二者都用"检索"思路，但对象不同：

| 概念 | 检索什么 | 目的 |
|------|----------|------|
| RAG | 外部知识库/文档 | 给模型补事实，减少幻觉 |
| 记忆 | 历史对话/过往经验 | 让 agent 跨轮连贯、不吃亏 |

```text
用户多轮对话
   │
   ▼
Agent 先"回忆"：从记忆里捞相关历史（也是一种检索）
   │
   ▼
再"查资料"：从 RAG 知识库捞相关文档
   │
   ▼
拼进 prompt → 模型作答
```

在 coding agent 里，"记忆"可能是"之前修过这个模块的哪几个文件"，"RAG"可能是"这个库的官方用法文档"。两者叠加，agent 才既"懂你"又"懂事"。

## 9.13 常见误区清单

写 RAG 时新手容易踩的坑，提前列出来避坑：

- **误区 1：块越大越好**。错，块大语义杂、检索准度降。应取"语义完整的最小单元"（如一个函数、一段小节）。
- **误区 2：检索到就直接全喂**。错，应 rerank 取 Top-N，否则噪声淹没信号。
- **误区 3：embedding 万能**。错，专有名词/版本号/函数名，关键词检索比 embedding 更准，需混合。
- **误区 4：一次性接好就完**。错，要评测召回率与忠实度，持续调切块/检索参数。
- **误区 5：RAG 能消灭幻觉**。错，它只是压低概率；检索不到或资料矛盾时，模型仍可能编。要配"没依据就直说不知道"。

> **注意 · 别把 RAG 当成银弹**
>
> RAG 提升的是"事实可得性"，不是"模型一定说真话"。真正可靠的系统 = 好检索 + 好提示（要求"只基于资料答"） + 引用溯源（标明答案出自哪段） + 必要的人的把关。RAG 是其中一环，不是全部。

## 9.14 本章关键点回顾

- LLM 有知识截止和幻觉；RAG 用"检索到的资料"替代"模型记忆"当事实源。
- RAG 三步：检索 → 增强（拼进 prompt）→ 生成。
- Embedding 把语义变成向量；向量库做"最近邻"检索。
- Chunking 切块质量直接决定 RAG 上限。
- 代码场景里，grep / 文件读取工具就是 coding agent 的"检索器"。

## 9.15 RAG 一句话心智模型

把整章收成一句可带走的话：

> **RAG = 回答前，先去外部把事实捞上来，再让模型基于事实说人话。**

它不神秘，不是某个数据库产品，而是一种"外接知识"的架构思路。在聊天机器人里，外部是向量库；在 coding agent 里，外部是 grep 结果、文件内容、web 搜索。形态各异，思路同源。当你以后再听到"给模型接个知识库"，脑里应该立刻浮出"检索 → 增强 → 生成"这三步，以及"切块、embedding、重排、评测"这四块工程实处。

## 9.16 在 coding agent 里落地 RAG 的最小步骤

如果你想给一个像 Pi 这样的 coding agent 接上"代码知识检索"，最小可行路径是这样的：

```text
① 建索引：把仓库按文件/函数切块 → 每块 embedding → 存向量库
        （或偷懒：直接暴露 grep / 符号索引工具，多数场景够用）
② 接工具：在 Context.tools 加一个 search_code(query) 工具，
           内部调用向量库（或 grep）
③ 写提示：systemPrompt 里告诉模型"遇到不熟悉的代码先调 search_code"
④ 跑循环：模型遇事先检索 → 把相关片段拼进上下文 → 再作答/改代码
⑤ 评测：造几个"某功能在哪实现"的问题，看检索召回率与最终答对率
```

> **提示 · 别一上来就上向量库**
>
> 对代码检索，先试 `grep` + 文件读取工具（第 7、10 章的原生能力）。等仓库大到 grep 扛不住、或需要"语义级"找相似代码时，再引入 embedding + 向量库。这是 Pi "轻内核、按需加能力"哲学在 RAG 上的直接应用——也呼应第 10 章"先问真需要协议/重依赖吗"。

## 9.17 延伸：RAG 与"微调"有什么区别

新手常把 RAG 和微调（Fine-tuning）混为一谈，其实目的不同：

| 做法 | 改的是什么 | 适合解决 |
|------|------------|----------|
| RAG | 不改模型，回答时外挂资料 | "模型不知道的事实/最新信息" |
| 微调 | 改模型权重，让它更会某种风格/任务 | "模型不会某种能力/语气" |

一句话：**RAG 补"知识"，微调补"能力"**。想让模型"知道你公司内幕"，用 RAG；想让模型"更会写某种格式的代码"，才考虑微调。很多生产系统两者并用，但 RAG 永远是更快、更可控的第一步——因为换资料不用重训模型。
