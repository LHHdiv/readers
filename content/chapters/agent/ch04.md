> 协议决定上限：模型能多好地使用工具，很大程度上取决于你的协议设计，而不是模型本身。

## 工具描述即提示词

模型看到的不是你的函数实现，而是函数的**描述**。一份好的工具描述包含三件事：

- 这个工具*什么时候*应该被调用；
- 每个参数的含义与取值边界；
- 失败时会返回什么。

`description` 写得越接近「给新同事写的说明书」，调用质量越高。

## 一个最小可运行的例子

```python
tools = [{
    "name": "search_docs",
    "description": "在知识库中检索与查询相关的文档片段。当问题需要事实依据时调用。",
    "parameters": {
        "type": "object",
        "properties": {
            "query": {"type": "string", "description": "自然语言查询"},
            "top_k": {"type": "integer", "default": 5}
        },
        "required": ["query"]
    }
}]
```

运行时的职责是：解析模型输出 → 校验参数 → 执行函数 → 把结果以 `tool` 角色回灌给模型。

## 三种协议路线对比

| 路线 | 约束位置 | 优点 | 代价 |
| --- | --- | --- | --- |
| Function Calling | 模型服务端 | 结构化稳定 | 被供应商锁定 |
| MCP | 独立协议层 | 工具可复用、跨进程 | 多一层运维 |
| ReAct 文本协议 | 提示词 | 任何模型可用 | 解析脆弱 |

## 错误处理是协议的一部分

工具失败时，不要替模型掩盖错误。把错误原样返回，并附一句可读的解释。多数模型都懂得换个参数重试。

> 经验法则：**让失败显式化**，智能体才有自愈的可能。

## 本章小结

- 工具描述的质量约等于调用成功率；
- 三种协议路线按团队约束选择；
- 错误回传是协议的一部分，不是异常。

## 练习

1. 给 `search_docs` 增加一个 `filter` 参数，观察模型是否正确学会使用它。
2. 故意让工具以一半概率失败，记录智能体的重试轨迹并分析。
